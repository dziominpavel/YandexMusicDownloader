## Context

Сейчас защита от дублей — только точная: `ErrAlreadyExists` по имени файла в `OUTPUT_DIR` и пропуск повторяющегося ID внутри плейлиста (`batch.go`). Имя файла намеренно искажено правилом сортировки кириллицы (`downloader/file.go`: префикс `ι `, замена первого символа на кириллический двойник), а чужая коллекция может быть названа как угодно. Мотивация и объём — в `proposal.md`, требования — в `specs/library-index/spec.md` и `specs/track-download/spec.md`.

Код уже содержит всё нужное для чтения тегов: `bogem/id3v2` (MP3), `go-flac/flacvorbis` (FLAC), `tommyo123/mtag` (M4A) — те же библиотеки, что пишет `internal/tagger`.

## Goals / Non-Goals

**Goals:**

- Поймать «тихий» дубль: другой порядок исполнителей, иное написание, кавер/версия, другой формат — и честно спросить пользователя.
- Не замедлить привычный сценарий: при выключенном `LIBRARY_DIR` — ноль изменений; при включенном — проверка миллисекундная.
- Первый запуск на большой коллекции не блокирует окно.

**Non-Goals:**

- Автоматическое удаление/перезапись дублей — только предупреждение и выбор пользователя.
- Анализ коллекции и статистика — отдельное предложение (`docs/13-collection-analysis.md`), вне этого change.
- Использование API Яндекса и ID треков для проверки (в коллекции возможны файлы из любых источников).
- TUI/горячие клавиши, изменение привычного сценария «ссылка → Скачать».

## Decisions

### 1. Кэш-файл + инкремент по size/mtime (вариант A)

Индекс живёт в JSON-файле рядом с exe (рядом с `.env`, тот же паттерн). При отсутствии кэша — полное сканирование; далее только `stat` каждого файла и перечитывание тегов у изменившихся.

- Альтернатива «сканировать на каждый клик» — отвергнута: чтение тегов тысяч FLAC занимает секунды-десятки, кнопка «Скачать» подвисала бы.
- Альтернатива «полное сканирование на старте в фоне без кэша» — отвергнута: каждый запуск платил бы полную цену.
- Запись кэша — атомарно (`temp → rename`), как принято в проекте для публикации файлов; в кэше — версия схемы, чтобы несовместимый формат пересоздавался молча.

### 2. Новый пакет `src/internal/library`

Изоллированный пакет: обход (`filepath.WalkDir`), чтение тегов по расширению (тот же dispatch, что в `tagger.Write`), нормализация, кэш, поиск. Отдаёт наружу один API примерно вида `FindMatches(artist, title, ext) []Match` с процентом схожести и путём. Пакет ничего не знает про UI и про downloader — только про файлы на диске.

- Почему не в `downloader`: там сетевой пакет, индекс — чисто локальная вещь; их связывает только вызов из `ui`.

### 3. Источник метаданных: теги первичны, имя файла — фолбэк

Теги (`artist`/`title`) читаются теми же библиотеками, что уже в `go.mod`. Если тегов нет или они пусты — разбор имени файла `Исполнитель - Название.ext` (с отбросом ведущего номера трека). Если и это не помогло — файл участвует в индексе только как путь и не даёт кандидатов.

- Альтернатива «только имена файлов» — отвергнута: в чужих коллекциях имена произвольные (`01 - Песня.flac`, `sflkj.mp3`).
- Альтернатива «только теги» — отвергнута: файлы без тегов не дали бы никакой защиты.

### 4. Схожесть: своя реализация, без новых зависимостей

Нормализация одинакова для обеих сторон (и для индекса, и для метаданных из API):

```text
  lowercase + ё->е + схлопнуть пробелы/тире/кавычки
       -> снять "ι " и свернуть лат.-кирил. двойники (первый символ)
       -> из имени файла убрать ведущий номер "01 - "
       -> список исполнителей: токены -> сортировка -> склейка
```

Правило сортировки (двойники, `sortPrefix`) уже реализовано в `downloader/file.go` — его нужно **вынести в общий пакет** (например `internal/norm`), чтобы правило жило в одном месте и не расходилось; `downloader` продолжает использовать его для имён файлов, `library` — для обратной нормализации.

Оценка: `simTitle = 1 - Levenshtein/maxLen` по нормализованным заголовкам, `simArtists` — по нормализованным спискам. Срабатывание: `simTitle >= 0.90`, либо `simTitle >= 0.80 && simArtists >= 0.90` (точный набор констант — в задачах, настраиваемый параметр в `.env` отложено). Лучший кандидат (максимальный балл) показывается в диалоге.

- Альтернатива библиотеки Levenshtein — отвергнута: на коротких строках своя реализация тривиальна (окно Дамерау-Левенштейна ~40 строк), зависимость не оправдана.
- Альтернатива триграмм/Жаккард — рассматривалась как дешёвый предфильтр на больших коллекциях: начать с линейного перебора с ранним отсечением по разнице длин, при реальной необходимости (десятки тысяч файлов) добавить предфильтр.

### 5. Диалог подтверждения — нативный Wails `MessageDialog`

Блокирующий вопрос («Возможен дубль: … Скачать?») показывается из Go в точке перед скачиванием — фронтенд уже ждёт промис `Download`, дополнительных контрактов не нужно.

- Альтернатива — модалка в `index.html`: выигрывает списком кандидатов и стилем, но требует нового контракта event/call. Если позже захотим показывать несколько кандидатов сразу — это замена одного решения в том же месте, спеки не меняются.

### 6. Порядок проверки внутри `ui.App.Download`

```text
  ссылка -> resolver.Parse
             |
             +-- плейлист -> Playlist() -> для каждого трека:
             |                         нормализация -> FindMatches
             |                         -> есть кандидаты? -> диалог
             |                              Да  -> качать
             |                              Нет -> [skip] (дубль), строка в лог
             |
             +-- трек -> fetchTrack -> те же шаги -> client.Download
```

Существующие проверки (`already exists`, `duplicate` по ID) остаются на своих местах ниже по конвейеру.

### 7. Свежесть индекса в пределах сессии

Файл, только что скачанный в `OUTPUT_DIR`, добавляется в индекс сразу после публикации (в том же событии, где сейчас происходит `temp → rename`), без повторного сканирования. Это закрывает кейс «скачал — тут же вставил ту же ссылку».

## Risks / Trade-offs

- [Ложные срабатывания на общих названиях («Love», «Прости»)] → принято пользователем: текст диалога прямо говорит «возможно» и показывает оба файла с процентом; лишний клик лучше пропущенного дубля. Порог вынесен в константу, легко подкрутить.
- [Кэш устаревает: файл перезаписан с тем же размером и mtime] → маловероятно для музыки; кэш хранит и mtime, и size; полное пересканирование доступно удалением кэш-файла. Явный «пересканировать» — вне этого change.
- [Первый запуск на 50k файлов занимает минуты] → индексация в фоне, окно живое, в логе счётчик; проверка идёт по уже проиндексированной части с `[warn]` о неполноте.
- [Много окон подтверждения в большом плейлисте] → диалог только при попадании выше порога; отказ по одному треку не останавливает остальные (закреплено в спеке).
- [Конкурентность: индексация в фоне + скачивание в воркерах] → доступ к индексу под мьютексом; запись кэша атомарная.
- [Правило сортировки живёт в `downloader`, а обратная нормализация нужна в `library`] → вынос в `internal/norm` до начала работы с индексом; риск расхождения правил снимается единством источника.

## Migration Plan

Фича отключена без `LIBRARY_DIR` — миграция не требуется, откат = убрать параметр из `.env`. Кэш-файл создаётся сам и безопасно удаляется в любой момент. Документация: `.env.example` и README/`docs` пополняются описанием `LIBRARY_DIR`.

## Open Questions

- Нужен ли пользовательский порог схожести в `.env` (`LIBRARY_SIMILARITY`)? В v1 — константа; параметр добавим, если реальная эксплуатация покажет, что 0.90 не подходит.
- Показывать ли в диалоге все кандидаты, а не только лучший? Зависит от нативного формата окна (одна строка vs список) — решается при реализации, спеки не меняются.
