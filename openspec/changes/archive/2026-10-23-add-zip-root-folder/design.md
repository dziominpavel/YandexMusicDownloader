# Design

## Context

См. `proposal.md` — Why. Технический контекст, влияющий на подход:

- `scripts/pack-zip.ps1` — единственное место, где собирается дистрибутивный zip; `release.ps1` только проверяет наличие ассетов в `dist/` и публикует их как есть.
- Сейчас `pack-zip.ps1` вызывает `Compress-Archive -Path $appExe, $ffmpeg`: оба файла лежат в корне архива.
- `release.ps1` синхронизируется между репозиториями (шапка скрипта, `SCRIPT_VERSION`), поэтому менять его под проектную структуру zip нельзя.
- Витрина читает метаданные последнего релиза и отдаёт файл; содержимое zip она не разбирает.
- `app.exe` ищет `ffmpeg.exe` рядом с собой через `filepath.Dir(exe)` (`src/internal/downloader/convert.go`), поэтому оба файла обязаны лежать в одной папке.
- Проверено на этой машине: `Compress-Archive` для каталога пишет имена записей с обратными слэшами (`YandexMusicDownloader\app.exe`), а `ZipArchive` с явным именем `YandexMusicDownloader/app.exe` — с прямыми, и `Expand-Archive` распаковывает его в правильную папку.

## Goals / Non-Goals

**Goals:**

- Один предсказуемый корневой каталог `YandexMusicDownloader` в zip, внутри — ровно `app.exe` и `ffmpeg.exe`.
- Сборка падает, если структура архива нарушена, — до того, как zip попадёт в релиз.
- Не менять общий `release.ps1`, имя zip и контракт витрины.

**Non-Goals:**

- Самораспаковывающийся архив или установщик.
- Добавление в архив `.env.example`, README, лицензий и других файлов.
- Автообновление приложения и версионирование папки.
- Изменение состава файлов или логики работы `app.exe`.

## Decisions

**1. Постоянное имя корневого каталога `YandexMusicDownloader`, без версии и платформы.**
Версия уже есть в имени zip и теге релиза; постоянное имя позволяет распаковать новую версию поверх старой папки, сохранив `.env` и `downloads/`. Версия в имени папки привела бы к накоплению `YandexMusicDownloader-0.2.0`, `-0.3.0` и т.д. Вариант `YandexMusicDownloader-win-x64` отклонён: платформа одна, а имя становится длиннее.

**2. Сборка через `System.IO.Compression.ZipArchive`, а не `Compress-Archive`.**
`ZipArchive` позволяет задать имена записей явно (`YandexMusicDownloader/app.exe`) и получить корректные прямые слэши, которые понимают не только Windows, но и GitHub, 7-Zip, macOS/Linux. `Compress-Archive` на Windows PowerShell 5.1 пишет обратные слэши — Windows проводник их понимает, но это нестандартный zip. Дополнительный плюс: не нужно копировать 107 МБ `app.exe` + `ffmpeg.exe` во временную папку, запись идёт сразу в архив.
Альтернативы:
- *Временная папка + `Compress-Archive`* — отклонена из-за обратных слэшей и лишнего копирования.
- *Ручное создание записей через `Compress-Archive` с `-Path` на файлы и переименование* — невозможна: cmdlet не даёт управлять именами внутри архива.

**3. После сборки — проверка содержимого архива и удаление битого результата.**
Скрипт открывает готовый zip только на чтение и сверяет множество записей с ожидаемым: ровно `YandexMusicDownloader/app.exe` и `YandexMusicDownloader/ffmpeg.exe`. Любое расхождение — сообщение и `exit 1`, zip удаляется, чтобы старая или неполная сборка не уехала в `dist/`. Это дешевле, чем ловить структуру на этапе релиза, и не требует правок общего `release.ps1`.

**4. `release.ps1` не трогаем.**
Он общий для нескольких проектов и публикует верхнеуровневые ассеты `dist/`. Проверка структуры zip — ответственность проекта-источника, то есть `pack-zip.ps1`. Если добавить проверку в общий скрипт, его копии разойдутся между репозиториями.

**5. Состав архива — только `app.exe` и `ffmpeg.exe`.**
`.env` приложение создаёт само через настройки; `.env.example` и README дублировали бы встроенную справку и описание на витрине. Это осознанно оставлено за рамками: если понадобится README для друзей, это отдельное расширение состава.

**6. Имя zip не меняется.**
Остаётся `YandexMusicDownloader-<version>-win-x64.zip` — по конвенции релиза и для совместимости с витриной. Меняется только внутренняя структура.

**7. Двойная вложенность при распаковке проводником принимается.**
Windows «Извлечь всё» создаёт папку по имени архива, внутри которой лежит `YandexMusicDownloader/`. Это стандартное поведение zip с корневым каталогом; пользователь всё равно получает один предсказуемый каталог приложения. В `docs/friends-setup.md` шаг распаковки формулируется так, чтобы это не выглядело ошибкой.

**8. Документация и changelog — часть изменения.**
`docs/friends-setup.md`: после распаковки открыть `YandexMusicDownloader\app.exe`, `.env` создастся рядом. `CHANGELOG.md`: пользовательский блок `**Изменено**` («архив распаковывается в папку...») и инженерные детали под `### Изменено`. Правки в `docs/friends-setup.md` и `CHANGELOG.md` пересекаются с change'ем `add-token-help` — при применении обоих изменения сводятся вручную.

## Risks / Trade-offs

- [`ZipArchive` требует сборки `System.IO.Compression` и `System.IO.Compression.FileSystem` в Windows PowerShell 5.1] → в скрипте явные `Add-Type -AssemblyName` для обеих сборок; проверить запуск именно в `powershell.exe` 5.1, а не только в PowerShell 7.
- [Проверка структуры может отстать от состава архива, если в будущем добавят файл] → ожидаемый список записей задаётся одной константой в скрипте; при расширении состава её обновляют вместе с задачей.
- [Двойная вложенность при «Извлечь всё» может удивить] → описано в `docs/friends-setup.md`; это не ошибка упаковки.
- [Старые пользователи распакуют новую версию рядом со старыми `app.exe`/`ffmpeg.exe`] → в доке указано распаковывать в новую папку; старые плоские файлы можно удалить вручную. Автоматической миграции нет — приложение портативное.
- [Сжатие двух больших exe через `ZipArchive` может идти дольше, чем `Compress-Archive`] → уровень `Optimal` сохраняет прежний размер; упаковка выполняется один раз на релиз, не в рантайме.
- [Витрина может ожидать файлы в корне zip] → проверено: витрина только отдаёт ссылку на ассет и не распаковывает его; имя и формат файла не меняются.

## Migration Plan

Отдельной миграции данных нет: `.env`, `downloads/` и `library-index.json` остаются рядом с exe. При выпуске следующей версии zip будет собран с новой структурой; старые релизы не перезаписываются. Откат — `git revert` изменения `pack-zip.ps1` и выпуск следующей версии со старой плоской структурой; прочитанные ранее `.env` и `downloads/` от этого не страдают.

## Open Questions

Нет: имя папки, состав и судьба `release.ps1` решены.
