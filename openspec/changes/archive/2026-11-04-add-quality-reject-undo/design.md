# Design

## Context

Сейчас `quality.Journal` (v1) хранит отказы как `declined: { "<путь>": { track_id, until } }` — один кандидат на файл, TTL 180 дней. `App.DownloadFound` записывает отказ только как побочный эффект: если пользователь снял галочку с поискового совпадения и скачал остальные. После находки журнал помечает файл `lossless`, а `Checker.Check` пропускает такие записи до повторной проверки; `Decline` этого не сбрасывает. Поэтому отклонённый файл фактически выпадает из мониторинга.

Окно найденного строит строки как `<label>` с чекбоксом; отдельного действия отказа нет. Настройки уже имеют раздел «Мониторинг FLAC», куда логично добавить управление отказами.

В проекте параллельно идут `fix-ui-and-flac-upgrade` (меняет окно найденного, настройки и `quality-upgrade`) и `add-startup-animation` (правит те же frontend-файлы). Этот change нужно применять после них или поверх, сохранив их поведение.

## Goals / Non-Goals

**Goals:**

- Явно отклонять поисковое совпадение без скачивания и без изменения аудиофайла.
- Хранить несколько отказов на локальный файл, без автоматического истечения.
- Оставлять MP3 в мониторинге и искать другие версии после отказа.
- Показывать список отказов в настройках и позволять вернуть совпадение.
- Сохранить старые отказы при переходе журнала на v2.

**Non-Goals:**

- Откат уже выполненного обновления и возврат MP3 из `_old`.
- Отклонение ID-совпадений и исправление неверных Yandex ID в тегах.
- Изменение алгоритма матчинга, сравнение длительности или распознавание ремиксов.
- Немедленный повторный поиск сразу после отказа: следующая проверка идёт по расписанию или по кнопке.
- Изменение правил публикации FLAC, `_old`, `OUTPUT_DIR`/`LIBRARY_DIR`.
- Бамп версии проекта: он выполняется только при релизе.

## Decisions

### 1. Журнал v2: список отказов на локальный файл

`journalVersion` поднимается до 2. Вместо одного `Declined` на путь хранится срез:

```go
type Declined struct {
    TrackID       string    `json:"track_id"`
    LocalLabel    string    `json:"local_label,omitempty"`
    MatchedArtist string    `json:"matched_artist,omitempty"`
    MatchedTitle  string    `json:"matched_title,omitempty"`
    MatchedAlbum  string    `json:"matched_album,omitempty"`
    MatchedYear   string    `json:"matched_year,omitempty"`
    Confidence    int       `json:"confidence,omitempty"`
    Exact         bool      `json:"exact,omitempty"`
    Codec         string    `json:"codec,omitempty"`
    DeclinedAt    time.Time `json:"declined_at,omitempty"`
}

Declined map[string][]Declined `json:"declined"`
```

Методы: `Decline(path, d)` заменяет запись с тем же `TrackID` и добавляет новую, `IsDeclined(path, trackID)`, `Undecline(path, trackID) (Declined, bool)`, `DeclinedList() []DeclinedItem`, `Forget(key)` для удаления записи проверки. `DeclinedItem` — плоская view-модель с `Path`, `FileName` и полями кандидата для настроек.

Альтернатива «один кандидат на путь» отклонена: второй отказ затирал первый, и отклонённый ранее трек мог вернуться. Альтернатива «глобальный список по TrackID» отклонена: один и тот же трек Яндекса может быть законным обновлением для другого локального файла.

`DeclinedTTL` больше не применяется к новым отказам. `Prune` по-прежнему удаляет записи для путей, которых больше нет в индексе: если локальный MP3 удалён, хранить отказ не для чего.

### 2. Миграция v1 без потери отказов

`Journal.load` читает версию из сырого JSON. Для v1 старые `declined: path -> {track_id, until}` конвертируются в срез из одной записи. Метаданные кандидата берутся из `entries["file:"+path]`, если там есть `StatusLossless`; иначе остаётся только `TrackID`. Просроченные v1-записи (`until` в прошлом) не переносятся: старый код считал их истёкшими. Миграция сразу сохраняется в v2; если запись не удалась, журнал остаётся мигрированным в памяти до следующего `Save`.

Альтернатива «поднять версию и забыть старые отказы» отклонена: пользователь уже мог отклонить ложные совпадения, и они вернулись бы после обновления.

### 3. Отклонение сбрасывает результат проверки файла

При отклонении:

```text
App.RejectFound(item)
  |
  +-- проверить: не busy, не checking, есть journal
  +-- проверить: item.MatchSource == "search", item.TrackID != ""
  +-- Journal.Decline(item.Path, Declined{...})
  +-- Journal.Forget("file:" + item.Path)   // убрать StatusLossless
  +-- Save, log, refreshPendingQuality()
  +-- вернуть оставшиеся FoundItem
```

Удаляется именно ключ `file:<path>`, а не запись кандидата `item.TrackID`: запись кандидата может использоваться другими файлами или ID-совпадениями. После удаления `file:<path>` `Checker.Check` снова видит файл как кандидата, `Pending` перестаёт показывать отклонённого, а `searchCandidate` отфильтрует его через `IsDeclined`.

Почему не оставить запись `lossless` и не научить `Checker` проверять `IsDeclined` перед пропуском: это возможно, но оставляет в журнале устаревшую «находку» и требует правок в двух местах. Удаление записи проще и сразу убирает предложение. Дополнительно в `Checker` остаётся защитная проверка: если `StatusLossless` всё же встретился, а его `MatchedTrackID` отклонён для этого пути, файл не пропускается.

### 4. Проверка после отказа и TTL 7 дней

`searchCandidate` уже фильтрует отклонённых кандидатов. Меняется только выбор TTL, когда кандидаты были, но все отфильтрованы:

- поиск не дал результатов или ни один не прошёл порог — `no_match` на 30 дней, как раньше;
- кандидаты были, но все отклонены — `no_match` на 7 дней (`AutoCheckInterval`).

Это отвечает на «вдруг выйдет ещё какая-то версия»: файл не ждёт 30 дней. Отклонённый кандидат при этом не возвращается, потому что `IsDeclined` проверяется до скоринга.

Альтернатива «не менять TTL» отклонена: при автопроверке раз в 7 дней файл с единственным отклонённым кандидатом фактически ждал бы 30 дней.

### 5. Возврат восстанавливает предложение без сети

`App.Undecline(path, trackID)`:

1. Удаляет запись из `declined` и возвращает её метаданные.
2. Если метаданные полные, собирает `Entry{Status: StatusLossless, Codec, MatchSource: "search", MatchedTrackID, MatchedArtist, MatchedTitle, MatchedAlbum, MatchedYear, Confidence, Exact}` и кладёт под `file:<path>`.
3. Сохраняет журнал, пишет лог, вызывает `refreshPendingQuality()` и возвращает оставшиеся `FoundItem`.

Так кандидат сразу возвращается в список и бейдж, без запроса к API. Если запись пришла из v1 без метаданных, `Entry` не восстанавливается: отказ снимается, а кандидат появится при следующей проверке. Это лучше, чем показывать в списке строку без названия.

Скачивание при возврате не запускается: пользователь только снимает запрет. Повторный отказ снова вызывает `RejectFound`.

### 6. UI окна найденного

`qualityRow` перестраивается: внешний `<div class="qrow">`, внутри `<label>` с чекбоксом и текстом, рядом — кнопка «Не тот трек» для `matchSource === "search"`. Вложенная кнопка в `<label>` недопустима: клик по ней переключал бы чекбокс.

По нажатию:

```text
RejectFound(item)
  -> qualityItems = ответ (оставшиеся)
  -> renderQualityList / updateQualitySummary / updateQualityBadge
  -> если список пуст: closeQuality()
  -> ошибка: qualityError.textContent
```

Кнопка скрыта для ID-совпадений и недоступна, пока идёт проверка или job'а. После удаления строки фокус переходит на следующую кнопку отказа или на «Скачать», а при закрытии окна — в поле ссылки, как сейчас.

### 7. UI настроек: список отказов и «Вернуть»

В раздел «Мониторинг FLAC» добавляется подраздел «Отклонённые совпадения»:

```text
+--------------------------------------------------------------+
| Мониторинг FLAC                                              |
| [x] Проверять наличие FLAC автоматически                     |
| [Проверить сейчас]  FLAC: ...                                |
|                                                              |
| Отклонённые совпадения                                       |
| +----------------------------------------------------------+ |
| | Artist - Song.mp3                 03.11.2026  [Вернуть] | |
| |   Найдено: Artist - Song (Remix)                         | |
| +----------------------------------------------------------+ |
| | ...                                                       | |
+--------------------------------------------------------------+
```

`Settings` получает `QualityRejected []quality.DeclinedItem`; `GetSettings` заполняет его из журнала. Список сортируется по `DeclinedAt` (новые сверху), затем по пути. `#sRejectedList` имеет ограниченную высоту и прокрутку, `#sRejectedEmpty` показывает «Отклонённых совпадений нет». Кнопка «Вернуть» вызывает `UndoReject(path, trackID)`, удаляет строку и обновляет бейдж по возвращённому списку `FoundItem`. Подтверждение не нужно: действие обратимо повторным отказом.

Во время проверки кнопки «Вернуть» неактивны, чтобы не спорить с `Checker`, который пишет журнал. Во время job'ы настройки и так закрыты существующим правилом.

### 8. Контракты UI и события

- `App.RejectFound(item quality.FoundItem) ([]quality.FoundItem, error)`
- `App.UndoReject(path, trackID string) ([]quality.FoundItem, error)`
- `Settings.QualityRejected []quality.DeclinedItem`
- После обоих действий backend эмитит `quality-pending` с оставшимся списком; фронтенд обновляет бейдж и, если окно найденного открыто, список.
- В лог: `[reject] <локальный файл>: <найденный трек> — больше не предлагать` и `[reject] ... — возвращено`.
- Ошибки отклонения/возврата (идёт проверка, устаревший элемент, ID-совпадение) возвращаются на русском и показываются в `qualityError`/`settingsError`.

### 9. Совместимость с параллельными changes

`fix-ui-and-flac-upgrade` уже меняет окно найденного, раздел настроек и `quality-upgrade`; `add-startup-animation` правит те же `index.html`/`app.css`. В tasks первым шагом фиксируется порядок: дождаться завершения или наложить поверх, затем проверить, что кнопка «Не тот трек» и список отказов живут в актуальной версии окна/настроек. Если `fix-ui-and-flac-upgrade` уберёт кнопку FLAC из шапки, наш список всё равно остаётся в настройках, а окно найденного открывается оттуда же.

## Risks / Trade-offs

- **Устаревшее восстановленное предложение** → `DownloadFound` при скачивании заново проверяет lossless и при fallback не трогает старый файл; пользователь увидит ошибку и сможет проверить снова.
- **Список отказов растёт без TTL** → `Prune` удаляет записи для исчезнувших локальных файлов; объём записей мал, ручной очистки в v1 не добавляем.
- **Гонка с проверкой** → отклонение и возврат запрещены во время `checking`; кнопки неактивны, backend возвращает ошибку.
- **Миграция v1** → старые просроченные отказы не переносятся; активные переносятся с метаданными из `entries`, если они есть. Тест на миграцию обязателен.
- **Откат на старую версию** → старый exe не читает журнал v2 и пересоберёт его; отказы будут потеряны. Журнал — кэш, это допустимая цена.
- **ID-совпадения по-прежнему нельзя отклонить** → это осознанно: ID считается идентичностью файла; неверный ID — отдельная задача про теги.
- **Ложное совпадение всё ещё может появиться до первого отказа** → это ограничение матчинга, а не хранения; улучшение матчинга (длительность/версии) вне этого change.

## Migration Plan

1. Журнал v1 читается, конвертируется в v2 и сразу сохраняется при загрузке; при ошибке записи остаётся в памяти до следующего `Save`.
2. `.env`, индекс, `_old` и правила публикации не меняются.
3. Откат: вернуть предыдущий exe; журнал v2 будет проигнорирован и пересобран, отказы потеряются. Это документируется в `docs/15-flac-monitor.md`.
4. Пользовательские пункты и инженерные детали добавляются в `CHANGELOG.md` в `[Unreleased]`; версия проекта не меняется.

## Open Questions

Нет. Решения об ID-совпадениях, отсутствии TTL, TTL 7 дней для «все отклонены» и немедленном восстановлении из метаданных приняты в этом design.
