# Design

## Context

См. `proposal.md` — Why. Текущий старт: `main` открывает лог, вызывает `ui.NewApp()` (читает `.env`, проверяет токен через `config.Validate` с таймаутом 15 с, создаёт `downloader.Client`), затем `wails.Run` создаёт окно 950×634 с `BackgroundColour #12100F`, а WebView2 загружает встроенные `dist/*`. Фронтенд — vanilla IIFE в `app.js`, стили в `app.css`; `//go:embed dist/*` включает только файлы корня `dist`. Тест `tests/statusbar_check.js` исполняет `app.js` в VM с DOM-заглушкой, где нет `setTimeout`, но есть `requestAnimationFrame`, `window.go` и `window.runtime`.

Ограничения: один exe, WebView2, русские тексты, отсутствие новых runtime-зависимостей, сохранение текущих биндингов и событий, никаких изменений в downloader/resolver/tagger/library/quality. Wails v2 не имеет отдельной опции splash screen; в `options.App` есть `StartHidden`, `Frameless`, `BackgroundColour`.

## Goals / Non-Goals

**Goals:**

- Первый кадр страницы — брендовая заставка Warm Vinyl примерно на секунду.
- Окно и главный экран не ждут сетевой проверки токена.
- Заставка не блокирует ввод, не ломает тесты и исчезает при сбое JS.
- Сохранить vanilla-стек, один exe и текущую визуальную систему.

**Non-Goals:**

- Нативное Win32-окно заставки, frameless-окно, кастомный title bar.
- Видео, GIF, APNG, Lottie, Rive и любые новые библиотеки.
- Прогресс-бар, звук, кнопка «Пропустить», заставка только при первом запуске.
- Изменение логики скачивания, настроек и форматов файлов.

## Decisions

### D1. Заставка — слой в странице, а не отдельное окно и не медиафайл

Решение: добавить в `index.html` фиксированный слой `#boot` поверх `.app-shell`. Он рисуется тем же HTML/CSS/SVG, что и остальной интерфейс, и использует существующий символ `icon-vinyl`.

Почему:

- слой появляется в первом кадре страницы и не требует второго окна;
- анимация весит единицы килобайт, резкая на 125–150% DPI и совпадает с палитрой;
- длительностью и снятием управляет один таймер, а не длительность видеофайла;
- слой остаётся контейнером: если позже появится видео, внутрь можно положить `<video>` без изменения тайминга и JS.

Альтернативы:

- **Нативное окно Win32** — покрывает даже время до `wails.Run`, но требует сотен строк платформенного кода, своего WndProc, DPI и обработки закрытия. Для личного приложения это неоправданный риск.
- **MP4/GIF** — фиксированный растр, нет альфы у H.264, мегабайты, размытие при масштабировании и невозможность закончить анимацию по готовности. Видео допустимо только как замена внутреннего знака позже.
- **Lottie/Rive** — новые рантаймы и шаг сборки; для одной анимации не нужны.

`StartHidden` используем: проверка реального окна показала, что Wails показывает окно после загрузки WebView2, и заставка успевает проиграть в скрытом окне. `StartHidden: true` + `OnDomReady -> runtime.WindowShow` показывают окно, когда страница готова; первый видимый кадр — заставка. Остальное время до окна — запуск WebView2, его HTML-анимация не закрывает.

### D2. Тайминг: фиксированная секунда от старта скрипта, синхронная с CSS

Решение: `BOOT_MIN_MS = 1000`, `BOOT_FADE_MS = 160`; при `prefers-reduced-motion` — `400` и без движения. В начале `app.js` слой получает класс `boot--run`, который запускает CSS-анимации; в тот же момент стартует таймер снятия. Через секунду добавляется `boot--done` (fade 160 мс), затем узел удаляется.

Почему фиксированная длительность, а не ожидание готовности: инициализация `app.js` синхронна, главный экран готов к моменту первого кадра; асинхронны только проверка токена и статус FLAC, и они не блокируют поле ввода. Ждать их под заставкой — значит снова привязывать старт к сети. Если позже появится настоящая загрузочная работа, добавим readiness-гейт отдельно.

```text
0 мс      фон #12100F, тёплое свечение
60 мс     диск: scale .92 -> 1, opacity 0 -> 1     (380 мс)
200 мс    борозды: вращение                         (6 с/оборот)
480 мс    wordmark: подъём 6 px + fade              (220 мс)
1000 мс   boot--done: fade 160 мс
1160 мс   узел удалён
```

Альтернатива: «ждать `window.go` + первый `requestAnimationFrame`» — на практике добавляет ту же секунду, но усложняет тесты и поведение на медленном WebView2.

### D3. Композиция и разметка

Решение: слой содержит мягкое радиальное свечение, знак винила из `icon-vinyl` и двухстрочный wordmark «Yandex Music / Downloader». Размер знака — около 104 px, цвета — `--accent`, `--text`, `--text-muted`, фон — `--bg`.

```html
<div id="boot" class="boot" aria-hidden="true">
  <div class="boot__glow"></div>
  <div class="boot__mark">
    <div class="boot__disc-wrap">
      <svg class="boot__disc" viewBox="0 0 24 24"><use href="#icon-vinyl"/></svg>
    </div>
    <div class="boot__word">
      <span class="boot__title">Yandex Music</span>
      <span class="boot__sub">Downloader</span>
    </div>
  </div>
</div>
```

Правила:

- `#boot` стоит после SVG-спрайта и до `.app-shell`, чтобы `use` уже был доступен.
- `position: fixed; inset: 0; z-index: 100; background: var(--bg)`.
- `pointer-events: none` — заставка декоративна и не мешает вводу; поле получает фокус сразу, как сейчас.
- `aria-hidden="true"`, внутри нет фокусируемых элементов.
- Анимируются только `opacity` и `transform`; `filter: blur()` не используем.
- Вращение — на самом SVG, вход — на обёртке, чтобы две анимации не конфликтовали за `transform`.
- Ноту и стрелку из `assets/icon.png` в первой версии не добавляем: линейный винил уже есть в UI и не требует нового ассета. Это визуальный вариант на потом.

### D4. Fail-open: статичный кадр по умолчанию и CSS-таймаут

Решение: дети заставки видимы по умолчанию; анимации включаются только под `.boot--run`. Если JS не выполнился, пользователь видит статичный знак, а слой сам исчезает по CSS-анимации с задержкой 3 с (`boot-failsafe`). Если JS выполнился, он снимает слой раньше.

Почему так:

- нет вспышки финального кадра: класс `boot--run` добавляется до первой отрисовки, а `from`-keyframe сразу переводит элементы в начальное состояние;
- при сбое JS экран не остаётся пустым;
- в тестовой VM нет `setTimeout` — код проверяет его наличие и удаляет слой сразу, не вешая прогон.

Дополнительно: `window.__yamdl.isBootDismissed()` отдаёт флаг снятия, чтобы `tests/statusbar_check.js` мог проверить fail-open без реального DOM.

### D5. Проверка токена уходит из пути до окна

Решение: разделить `apply` на два режима — `apply(cfg, validate bool)`.

- `NewApp` вызывает `apply(cfg, false)`: создаёт `downloader.Client` сразу, без сети, ставит `a.ready = "проверяю токен…"`, увеличивает `a.tokenGen`.
- `SaveSettings` вызывает `apply(cfg, true)`: сохраняет текущее поведение — записывает `.env`, валидирует токен, логирует результат, при отказе оставляет `a.client = nil`.
- `Startup` логирует `a.ready` и запускает `go a.verifyStartupToken(token, gen)`; проверка использует инъектируемое поле `a.validateToken` (по умолчанию `config.Validate`), чтобы тесты не ходили в сеть.
- Результат проверки пишется в `a.authErr` под `a.mu` и только если `gen == a.tokenGen`; иначе результат устарел (пользователь уже сохранил новый токен). Логирование — после отпускания мьютекса, потому что `a.log` сам его берёт.
- `a.client` фоновая проверка не меняет: иначе появился бы data race с `Download`. Вместо этого `Download` и `PreviewLink` сначала читают `a.authErr`; при невалидном токене возвращают понятную русскую ошибку, не закрывая окно.
- Пустой токен остаётся прежним путём: `a.client = nil`, сообщение про 30-секундное превью.

Почему не ждать проверку в `Download`: это вернуло бы блокировку до 15 с в первый же клик. Почему не обнулять `a.client` из горутины: это гонка с уже работающим UI; флаг ошибки достаточно, потому что все сетевые действия идут через `Download`/`PreviewLink`.

Альтернатива: `atomic.Pointer[downloader.Client]` — чище для конкурентного доступа, но требует правок во всех ~12 местах использования `a.client` и в тестах. Флаг ошибки даёт тот же пользовательский эффект меньшей ценой.

### D6. Проверки

- Go: `go test ./...`, `go vet ./...`, `go build ./...`; новые тесты на успешную/неуспешную/устаревшую проверку и на ошибку `Download`.
- JS: `node tests/statusbar_check.js` — существующие сценарии не меняются, добавляется проверка `isBootDismissed()`. Отдельный `tests/splash_check.js` — только если он не дублирует стенд: проверка наличия `#boot`, `aria-hidden`, ключевых кадров и `prefers-reduced-motion` в статике.
- Ручной визуальный прогон: 950×634 и 860×600, 125% и 150% масштаб Windows, скриншоты на 0/300/700/1000 мс, `prefers-reduced-motion`, холодный и тёплый старт.
- `openspec validate --all`, `python scripts/check-version.py`.

## Risks / Trade-offs

- **Секунда на каждый запуск начинает раздражать** → длительность в одной константе; при усталости уменьшается до 600–700 мс без переделки раскадровки.
- **Холодный старт WebView2 идёт до появления окна** → фон уже `#12100F`; окно показывается на `OnDomReady`, поэтому заставка не тратится в скрытом окне. Оставшееся время — запуск WebView2, его HTML-анимация не закрывает.
- **CSS-анимация на слабом GPU** → только `transform`/`opacity`, без blur и layout-свойств; reduced motion даёт статичный кадр.
- **Асинхронная проверка гоняется с сохранением настроек** → `tokenGen` отсекает устаревший результат; `authErr` под мьютексом.
- **Невалидный токен больше не обнуляет клиент** → `Download`/`PreviewLink` блокируются по `authErr`; фоновые проверки качества просто логируют ошибку API.
- **Тестовая VM без `setTimeout`** → guard и немедленное снятие; флаг `isBootDismissed` для проверки.
- **`//go:embed dist/*` не берёт подкаталоги** → новых файлов нет, разметка и стили остаются в корне `dist`.
- **Системный title bar виден всё время** → композиция центрированная, не «полноэкранное кино»; frameless вне скоупа.
- **Параллельная работа с `redesign-ui`** → заставка — изолированный слой и не переписывает существующие классы; перед правками сверить `git status` и не затирать незакоммиченные изменения.

## Migration Plan

Миграции данных нет: `.env`, API и форматы файлов не меняются. Версия не бампается, changelog только в `## [Unreleased]`.

1. Заставка: разметка, CSS, JS, fail-open, reduced motion.
2. Асинхронная проверка токена: `apply(cfg, validate)`, `verifyStartupToken`, guards, тесты.
3. Тесты и документация: `statusbar_check.js`, `docs/16-ui-design.md`, changelog.
4. Проверки и ручной визуальный прогон.

Откат: `git revert` изменений фронтенда и `app.go`; пользовательские данные не затрагиваются.
