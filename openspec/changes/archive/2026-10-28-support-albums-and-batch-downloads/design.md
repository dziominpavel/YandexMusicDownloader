# Design

## Context

См. proposal.md (Why). Текущая архитектура: resolver (только track/playlist), ui.Download принимает одну ссылку, downloader умеет скачивать плейлист пулом воркеров. Нужно добавить поддержку альбомов, множественные ссылки и ретраи.

## Goals / Non-Goals

**Goals:**
- Поддержать ссылки `.../album/{albumId}` (без trackId) — резолвить в список треков альбома
- Обрабатывать несколько ссылок в одном вводе (разделители: `\n`, `\r`, пробел, запятая)
- Добавить простые ретраи для временных сетевых ошибок при запросах/скачивании
- Максимально переиспользовать существующий пайплайн плейлиста (пул воркеров, прогресс, статусы, дубли, стоп)

**Non-Goals:**
- Изменение UI до полной карточной версии
- Подпапки по альбому/исполнителю
- Лирика, поиск, свои плейлисты
- Resume/dokachka

## Decisions

### 1) Resolver: добавить KindAlbum
- **Решение**: Расширить `resolver.Kind` (`KindTrack`, `KindPlaylist`, `KindAlbum`), добавить парсинг `^.../album/(\d+)(?:\?.*)?$` (но не конфликтует с `album/{id}/track/{id}` — проверять трек-паттерн первым).
- **Альтернатива**: Обрабатывать альбом как плейлист — нет, разные эндпоинты/формат ответа.
- **Рationale**: Минимально, явно.

### 2) Downloader: метод для альбома
- **Решение**: Добавить `Client.Album(id string) (*Playlist, error)` (используем ту же структуру `*Playlist` с `Title` и `Tracks` для единообразия с UI). Альбом можно получить через `GET /album/{id}` или через похожий механизм, как в Stmol/MarshalX. Нужно посмотреть, как это делается в референсах (docs/02, docs/05).
- **Альтернатива**: Преобразовывать альбом в плейлист-объект вручную в UI — менее чисто.
- **Рationale**: Единый путь в UI (`downloadPlaylist` уже умеет всё).

### 3) UI: множественные ссылки
- **Решение**: В `App.Download` парсить входную строку на список ссылок (сплит по whitespace/comma/newline), фильтровать пустые. Обрабатывать последовательно: для каждой ссылки вызывать тот же код (parse → track/playlist/album). Для некорректных ссылок логировать `[error]` и продолжать.
- **Альтернатива**: Параллельная обработка разных ссылок — риск путаницы в статусбаре/очереди.
- **Рationale**: Проще, предсказуемо, не ломает текущую модель "одна job'а".

### 4) Ретраи
- **Решение**: Добавить helper `retry.Do(fn, max int, backoff time.Duration)` в `internal/downloader` (или в `http` слое). Применять к:
  - `get` запросам (метаданные трека/плейлиста/альбома, account/status)
  - сетевым операциям при скачивании (особенно при получении direct link / скачивании байтов)
- Классифицировать ошибки: если это "not available"/"permission denied"/"not found" по бизнес-смыслу — не ретраить. Если сетевые (`net.OpError`, `context.DeadlineExceeded`, `io.EOF` в сетевом контексте) — ретраить.
- **Альтернатива**: Ретраи только на http уровне через транспорт — менее гибко.
- **Рationale**: Контролируемо, минимально.

## Risks / Trade-offs

- **[Риск]** Эндпоинт альбома может отличаться от плейлиста. → **Mitigation**: Сначала изучить `docs/02-repo-stmol.md` и `docs/05-repo-marshal.md`, при необходимости добавить маппинг под формат альбома.
- **[Риск]** Множественные ссылки — UX путаница в логах. → **Mitigation**: Для каждой ссылки явно логировать, использовать тот же формат, продолжать при ошибках отдельных ссылок.
- **[Риск]** Ретраи могут замедлить фейлы. → **Mitigation**: Малый максимум (3), бэкофф небольшой, ретраить только транзиентные ошибки.
- **[Trade-off]** Используем `*Playlist` для альбома вместо нового типа — чуть менее семантично, но сильно упрощает интеграцию. Приемлемо для текущего объёма.
