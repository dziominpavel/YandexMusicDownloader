# Design

## Context

Сейчас lossless-путь уже умеет всё, что нужно для обновления: `get-file-info` с подписью, выбор `flac`/`flac-mp4`, потоковую загрузку, AES-CTR, конвертацию ALAC→FLAC через `ffmpeg.exe`, теги и атомарную публикацию `temp → rename` (`src/internal/downloader/lossless.go`, `convert.go`). Не хватает трёх вещей:

- индекс коллекции не хранит Yandex ID и source URL — только исполнителя, название и расширение (`src/internal/library/library.go`, `meta.go`);
- нет отдельного «пробника» lossless: `losslessFileInfo` — внутренняя функция скачивания, а `quality=lossless` в ответе не гарантирует lossless (решает `codec`);
- нет мониторинга, журнала проверок и окна, которое предлагает обновление.

Проверка на живых данных подтверждает сценарий: из 72 MP3 в `downloads/` 67 сейчас отдают `flac-mp4`, 5 — `aac-mp4`, 1 — `mp3`. В `F:\!Musik\Music` 102 MP3, из них только 10 имеют Yandex ID (все 10 — `aac-mp4`), остальные 92 — внешние, их можно искать только по исполнителю/названию. Мотивация и объём — в `proposal.md`, требования — в `specs/quality-upgrade/spec.md` и дельтах `library-index`, `app-settings`, `desktop-app`.

## Goals / Non-Goals

**Goals:**

- Переиспользовать существующий lossless-пайплайн, а не писать второй загрузчик.
- Сделать проверку дешёвой и тихой: один запрос на трек, без скачивания, с журналом и TTL.
- Обновлять файл на месте, не ломая имена, подпапки, `.lrc` и m3u.
- Не удалять старый файл безвозвратно: `_old` сохраняет его.
- Не скачивать поисковые совпадения без подтверждения.
- Не превращать «нет FLAC» в приговор при проблемах с токеном, Плюсом или подписью запроса.

**Non-Goals:**

- Фоновая служба/планировщик Windows при закрытом приложении.
- Автоматическое скачивание без подтверждения (в v1 — всегда окно).
- Апконверт MP3→FLAC или «улучшение» битрейта.
- Переименование/реорганизация коллекции, чистка `_old`.
- Сопоставление файлов без исполнителя/названия и без ID.
- M4A-кандидаты (ALAC/AAC) — вне v1; проверяются только MP3.
- Batch-эндпоинт `get-file-info/batch` в v1.
- Проверка целостности уже имеющихся FLAC.

## Decisions

### 1. Новый пакет `src/internal/quality`

Оркестрация выносится из `ui`, чтобы её можно было тестировать без Wails:

```text
App (ui)
  |-- quality.Checker
  |     |-- library.Index.Snapshot()
  |     |-- downloader.ProbeLossless(ctx, trackID)
  |     |-- downloader.SearchTracks(ctx, query)
  |     `-- quality.Journal
  `-- quality.Upgrader
        |-- downloader.Upgrade(ctx, track, oldPath)
        |-- os.Rename(oldPath -> _old/...)
        `-- library.Index.RemoveFile / AddFile
```

`Checker` не пишет файлы и не использует job-контекст скачивания. `Upgrader` — обычная job'а с `StartJob`/`Stop`, чтобы работали кнопка «Остановить», статусбар и строки треков. `ui.App` остаётся тонким: связывает пакет с настройками, индексом, логом и фронтендом.

Альтернатива «всё в `ui.App`» отвергнута: там уже 1100+ строк, а проверка/журнал/поиск требуют своих тестов. Альтернатива «всё в `downloader`» отвергнута: `downloader` — сетевой и файловый пайплайн, а мониторинг — политика над индексом и журналом.

### 2. Расширение индекса, а не второй обход

`library.Entry` получает `TrackID` и `SourceURL`. Источники:

- FLAC: Vorbis `YANDEX_TRACK_ID`; fallback — `COMMENT` с URL.
- MP3: UFID с owner `music.yandex.ru`; fallback — COMM с description `yandex-music-downloader:source-url`; из URL берётся `/track/(\d+)`.
- M4A: freeform `----:com.yandex-music-downloader:source-url`; fallback — comment/URL.
- Общий fallback: regex `(?:album/\d+/)?track/(\d+)` по любому source URL.

`cacheVersion` поднимается до 2: старый кэш игнорируется, один раз перечитываются теги всех 3049 файлов (в фоне, как сейчас). Чтение идёт пулом до 8 воркеров: последовательный скан 2988 файлов на медленном `F:` занимал десятки минут, параллельный заметно короче. Это дешевле, чем отдельный обход и второй кэш. `Snapshot()` отдаёт копию записей под мьютексом; `RemoveFile(path)` и `AddFile(path)` обновляют индекс после перемещения. M4A-поля в индексе сохраняются для будущего, но мониторинг v1 использует только `.mp3`.

`collect()` пропускает каталоги с именем `_old` на любом уровне (`filepath.SkipDir`). Это защищает и проверку дублей, и мониторинг от старых файлов.

Альтернатива «отдельный индекс для мониторинга» отвергнута: дублирование обхода, кэша и чтения тегов; плюс два индекса могут разойтись.

### 3. Индекс при пустом LIBRARY_DIR

Сейчас `setupLibrary` возвращает `nil`, если `LIBRARY_DIR` пуст. При включённом `FLAC_MONITOR` индекс должен строиться по `OUTPUT_DIR`, иначе мониторинг не увидит скачанное. Решение: `setupLibrary` создаёт индекс, если задан `LIBRARY_DIR` **или** включён `FLAC_MONITOR`; корни — `[LIBRARY_DIR, OUTPUT_DIR]` (пустые отбрасываются).

При этом проверка дублей включается отдельным флагом `duplicatesEnabled` (`LIBRARY_DIR != ""`), а не наличием индекса. Иначе пустой `LIBRARY_DIR` + мониторинг неожиданно включил бы диалоги о дублях. Это изменение поведения фиксируется в дельте `library-index`.

### 4. Сопоставление: ID → поиск → подтверждение

Порядок:

```text
файл
  |
  +-- TrackID из тегов? -- да --> probe(TrackID)          (точно)
  |
  +-- нет --> artist + title
                |
                +--> GET /search?text=...&type=track&page=0
                      |
                      +--> нормализация norm.Comparable/ArtistsKey
                            |
                            +--> title >= 0.90 && artist >= 0.90
                                  |
                                  +--> до 3 кандидатов в окно
```

- Поиск выполняется только при отсутствии ID; ID авторитетнее названия.
- Запрос — `исполнитель + " " + название`; если результатов нет, повтор по одному названию (исполнитель всё равно проверяется при скоринге).
- Очистка запроса: убрать ведущий номер трека и очевидные маркеры качества/формата (`[320]`, `[128]`, `[m4a]`, `[flac]`), не трогая `Remix`/`Live`/`Remaster`.
- Скоринг переиспользует `norm` и функцию Левенштейна из `library/match.go` (её нужно экспортировать как `Similarity`/`MatchScore` либо добавить `ScoreCandidate`).
- «Уверенное» совпадение для предвыбора — нормализованные исполнитель и название равны (100%); 0.90–0.99 показываются, но не предвыбираются.
- Несколько кандидатов: показываем до 3, лучший первым; пользователь выбирает.
- Отклонённое совпадение запоминается в журнале по локальному пути + найденному ID, чтобы не предлагать снова.

Альтернатива «искать всё через API по названию, даже при наличии ID» отвергнута: лишние запросы и риск перепутать версии. Альтернатива «только ID» отвергнута: 92 внешних MP3 остались бы вне фичи.

### 5. Пробник lossless и классификация ответа

В `downloader` добавляется:

```go
type Probe struct {
    Available bool
    Codec     string // flac, flac-mp4, mp3, aac-mp4, ...
    Quality   string // lossless, nq, smart_preview, ...
    Bitrate   int
}

func (c *Client) ProbeLossless(ctx context.Context, trackID string) (Probe, error)
```

- `Available` — только `isFLACCodec(codec)`; `quality=lossless` не используется как признак.
- `quality=smart_preview`/`preview` → `ErrPreview`, проверка останавливается.
- 401/403 → `ErrAuth`/`ErrForbidden`; проверка останавливается, журнал не обновляется массово.
- 404 → `ErrUnavailable`, запись «недоступен» с длинным TTL.
- 429/сеть → ретраи с бэкоффом, затем `ErrCheckFailed` с коротким TTL.
- UID аккаунта кэшируется в `Client` (`sync.Once`/мьютекс), чтобы не делать `account/status` на каждый трек. `DownloadTrack` тоже переиспользует кэш.
- Запросы троттлируются: ~200 мс между треками, последовательно. 83 кандидата ≈ 20 секунд; для больших коллекций — запас.
- `ProbeLossless` получает контекст проверки, а не job-контекст скачивания; это позволяет проверке не мешать активной загрузке.

Альтернатива «использовать `download-info`» отвергнута: он отдаёт только MP3/AAC и не показывает lossless. Альтернатива «batch-эндпоинт» отложена: для 83–3000 треков последовательный probe достаточно быстрый, а batch-подпись и парсинг — дополнительный риск.

### 6. Журнал `flac-quality.json`

Файл рядом с `library-index.json` (там же, где `.env`):

```json
{
  "version": 1,
  "accountUID": 1130000014679075,
  "hasPlus": true,
  "lastCompleted": "2026-11-03T18:00:00+03:00",
  "lastResult": { "found": 67, "error": "" },
  "entries": {
    "17805173": {
      "status": "lossless",
      "codec": "flac-mp4",
      "checkedAt": "2026-11-03T18:00:00+03:00",
      "nextCheck": "2026-12-03T18:00:00+03:00",
      "matchSource": "id"
    }
  },
  "declined": {
    "f:\\music\\a - b.mp3": "123456"
  }
}
```

- TTL: `no_lossless` — 30 дней; `error` — 1 день; `unavailable` — 90 дней; `lossless` — без повторной проверки, но фактическое скачивание всё равно пробует lossless заново.
- `lastCompleted`/`lastResult` обновляются после каждой завершённой проверки (включая «ничего не найдено» и «ошибка»); `lastAttempt` пишется в начале, чтобы окно могло показать идущую/упавшую проверку. Эти поля — источник для индикации в главном окне и настройках, без повторного API-запроса.
- Сброс при смене `accountUID` или `hasPlus=false → true`.
- `declined` — по локальному пути и найденному ID, TTL 180 дней; сброс — вручную (кнопка «сбросить отклонённые» можно отложить).
- Запись атомарная (`temp → rename`), версия схемы; битый файл игнорируется и создаётся заново.
- Записи, которых больше нет в индексе, вычищаются при сохранении.
- Журнал не содержит токен; source URL и track ID — не секреты.

Альтернатива «не хранить журнал, проверять всё каждый раз» отвергнута: 3000 запросов на старте и риск rate limit. Альтернатива «хранить в `.env`» отвергнута: журнал объёмный и машинный.

### 7. Триггеры и расписание

```text
Startup
  -> index.Refresh (фон)
     -> maybeAutoCheck()
        -> FLAC_MONITOR && lastCompleted старше 7 дней && !busy
           -> Checker.Check(ctx) в горутине
              -> events quality-check-*
```

- Ручная кнопка вызывает `App.CheckQuality()`; если идёт скачивание/обновление — возвращает понятную ошибку, вторая job'а не стартует.
- Автопроверка не запускается, пока индекс ещё сканируется, и не запускается при `busy`.
- Таймер — раз в час проверяет, не пора ли; фактический интервал — 7 дней от `lastCompleted`.
- При закрытом приложении проверок нет; на следующем старте `maybeAutoCheck` догоняет расписание.
- Если `FLAC_MONITOR` выключили во время проверки — проверка отменяется (read-only, без потерь). Если выключили во время обновления — job'а продолжается, как требует спека.
- Проверка не блокирует окно и не занимает статусбар; прогресс — строки в логе. Обновление — обычная job'а.

### 8. UI: кнопка, бейдж, окно

- В шапке рядом с `📂` и `⚙` появляется кнопка `FLAC` (иконка/текст) с бейджем количества найденного. Нет находок — бейджа нет; есть — `FLAC 67`.
- Рядом с кнопкой — компактная строка `FLAC: 03.11.2026 18:00 — найдено 67` (или `ничего не найдено`, `ошибка`, `проверок не было`). Она обновляется событием `quality-check-finished` и видна без открытия настроек; в настройках показывается та же информация подробнее. Это прямой ответ на «понимать, что автопроверка работает».
- Находка открывает модалку (в стиле `dupOverlay`/`settingsOverlay`):
  - заголовок «Найдено N треков в лучшем качестве»;
  - список с чекбоксами: локальный файл, `MP3 192 → FLAC`, для поиска — «Найдено: Artist — Title, Album (2020), 98%»;
  - ID-совпадения предвыбраны; поисковые — только 100%-совпадения;
  - кнопки «Скачать все», «Показать список» (сворачивает/разворачивает список), «Позже».
- «Позже», Escape и клик по фону закрывают окно; список и бейдж остаются.
- Клик по кнопке `FLAC` при наличии бейджа открывает окно снова.
- `App.CheckQuality()` возвращает сводку; найденные элементы уходят событием `quality-found` (JSON-массив) и хранятся в памяти до перезапуска. После перезапуска журнал позволяет пересобрать список без повторного probe (статус `lossless` + индекс).
- Событие `quality-check-finished` несёт `lastChecked`, `found`, `error`; фронтенд обновляет компактную строку в главном окне и раздел в настройках. Если проверка не нашла ничего, строка всё равно обновляется — именно по ней видно, что автопроверка отработала.
- `App.DownloadFound(items)` принимает выбранные пути/ID и запускает `Upgrader`. Это обычная job'а: `job-start`, `tracks`, `track-status`, `progress`, `job-end`, `log`.
- Фронтенд должен реагировать на `job-start` установкой `busy=true` и кнопки «■ Остановить», потому что job'а может стартовать не по клику «Скачать». На `job-end` — сброс.
- Настройки на время job'ы недоступны (существующий `busy`); проверка настройки не блокирует.
- После закрытия модалки/завершения job'ы фокус возвращается в поле ссылки.

### 9. Обновление на месте

`downloader.Upgrade(ctx, track, oldPath)`:

1. `ProbeLossless(track.ID)`; если нет lossless — `ErrNoFLAC`, старый файл не трогаем.
2. Вычисляет расширение:
   - `flac` → `.flac`;
   - `flac-mp4` + `ConvertM4A` + найденный `ffmpeg.exe` → `.flac` (ALAC→FLAC);
   - `flac-mp4` без ffmpeg/конвертации → `.m4a` (lossless).
3. `dest = filepath.Join(filepath.Dir(oldPath), stem(oldPath)+ext)` — не по `SUBDIR_TEMPLATE`, чтобы сохранить место и имя.
4. Если `dest` существует — читает TrackID из тегов; тот же трек → `ErrAlreadyExists` (предложить только переместить старый MP3); другой → `ErrDestConflict`.
5. Скачивает во временный файл в той же папке (`streamLosslessTemp`), конвертирует при необходимости, тегирует через `Tag`, публикует `publishTemp`.
6. Возвращает `Result{Path, Format, Fallback, Converted}`; старый файл не удаляет и не перемещает — это делает `Upgrader`, чтобы политика `_old` жила в одном месте.

`Upgrader` после успеха и `!Fallback`:

```text
if published.Path != oldPath:
    oldRoot = LIBRARY_DIR, если oldPath внутри него, иначе OUTPUT_DIR
    rel = relative(oldRoot, oldPath)
    oldDir = join(oldRoot, "_old", dir(rel))
    mkdir oldDir
    target = join(oldDir, base(rel))
    if exists(target): target = name + "." + timestamp + ext
    os.Rename(oldPath, target)
    index.RemoveFile(oldPath)
    index.AddFile(published.Path)
```

- Перемещение в пределах одного корня — тот же том, `os.Rename` мгновенный. Если `os.Rename` не удался (файл занят/read-only) — лог `[warn]`, новый FLAC остаётся, старый остаётся рядом; job'а не считается упавшей.
- `.lrc` не перемещается: имя stem не меняется, лирика остаётся рядом с новым файлом. Если старый файл был в `_old`, `.lrc` остаётся в исходной папке и продолжает соответствовать новому FLAC.
- Существующий `.flac` с тем же треком: `Upgrader` не качает, а выполняет только перемещение старого MP3 в `_old` (после проверки TrackID).
- Concurrency: 2 воркера (ffmpeg CPU-heavy), независимо от `PLAYLIST_WORKERS`. `Stop` проверяется перед каждым треком и внутри загрузки; уже обновлённые остаются, текущий temp удаляется.
- Сводка job'ы: `[finished] X ok, Y skip, Z error`; `ok` — обновлённые, `skip` — уже lossless/отклонённые, `error` — сбои. Остановка — `[stopped]`.

### 10. Ошибки и защита от ложных статусов

| Ситуация | Статус | Журнал | Окно |
|---|---|---|---|
| `codec=flac/flac-mp4` | найден | `lossless` | да |
| `codec=mp3/aac-mp4` | нет FLAC | `no_lossless`, 30 дней | нет |
| `smart_preview`/`preview` | ошибка доступа | не менять | сообщение |
| 401 | ошибка токена | не менять | сообщение |
| 403 | трек недоступен (серия из 3 — стоп) | `unavailable`, 90 дней | нет |
| 404 | трек недоступен | `unavailable`, 90 дней | нет |
| 429/сеть после ретраев | ошибка | `error`, 1 день | нет (только лог) |
| MP3-fallback при обновлении | не обновлён | `no_lossless`, 30 дней | нет |
| ошибка публикации/тегов | не обновлён | `error`, 1 день | нет |

Ключевое: ошибки доступа **не** превращаются в «FLAC нет». Иначе один протухший токен пометит всю коллекцию на 30 дней.

### 11. Настройки и горячее применение

- `Config.FlacMonitor bool` (`FLAC_MONITOR`, default false; `1/true/yes/on`).
- `Settings.FlacMonitor` в `GetSettings`/`SaveSettings`; `config.Write` пишет ключ, комментарии и порядок сохраняются.
- `apply(cfg)` обновляет `a.cfg`; планировщик читает флаг под мьютексом. Включение не запускает проверку мгновенно — её запустит ближайший тик/старт или кнопка «Проверить сейчас» (в настройках и в шапке).
- `LIBRARY_DIR`/`FLAC_MONITOR` изменились — текущая проверка отменяется, индекс пересобирается существующим путём.
- Интервал 7 дней — константа v1; вынести в `.env` можно позже без изменения спек.

### 12. Тестируемость

- `quality.Checker` принимает интерфейсы `Snapshotter`, `Prober`, `Searcher`, `Journal`, `Clock`; тесты без сети и без Wails.
- `downloader.ProbeLossless`/`SearchTracks` тестируются на `httptest` с фикстурами ответов.
- `Upgrader` тестируется с подменённым `UpgradeFunc` и временным деревом: `_old`, коллизия имён, fallback, stop.
- Индекс: фикстуры MP3/FLAC/M4A с ID и без, `_old`, версия кэша.
- UI: события `quality-*`, состояния кнопки, модалка, фокус, обновление строки «последняя проверка» после автопроверки и после перезапуска.

## Risks / Trade-offs

- [Ложное поисковое совпадение] → показываем найденный трек, альбом, год и процент; предвыбираем только 100%-совпадения; скачивание только после подтверждения; отклонённое запоминается.
- [Яндекс сменит ключ подписи `get-file-info`] → probe вернёт 403; проверка остановится с сообщением о токене/протоколе, а не пометит коллекцию «FLAC нет». Это же затронет обычное скачивание — отдельная известная хрупкость протокола.
- [Нет `ffmpeg.exe`] → `flac-mp4` сохранится как lossless `.m4a`; в логе будет формат и причина. Пользователь может положить ffmpeg и повторить.
- [Диск: 67 FLAC ~1.5–2 ГБ + `_old` ~400 МБ] → `_old` не удаляется автоматически; в логе и окне показываем, куда уходит старый файл; чистка — вручную (кнопка — позже).
- [Первый запуск после смены версии кэша] → один раз перечитываются теги 3049 файлов; это фон, окно живо, в логе прогресс `[index]`.
- [Индекс устарел, пока идёт проверка] → проверка использует снимок; после обновления файлов индекс обновляется точечно; следующий цикл видит актуальное.
- [Пользователь правил теги старого MP3] → старый файл сохраняется в `_old` со всеми правками; новый FLAC получает свежие теги из API. При необходимости пользователь может вернуть старый файл.
- [Rate limit/429] → троттлинг 200 мс, ограниченные ретраи, остановка проверки; журнал не портится.
- [Имена не по текущему шаблону] → обновление на месте сохраняет старое имя; переименование — отдельная фича.
- [Настройки меняются во время проверки] → проверка отменяется; журнал частичный, следующий запуск продолжит.
- [Очень большая коллекция] → проверка может идти минуты; прогресс в логе, отмена при закрытии/выключении; batch-эндпоинт — возможное улучшение.

## Migration Plan

1. Фича выключена по умолчанию (`FLAC_MONITOR=false`) — существующее поведение не меняется.
2. `cacheVersion` 2: старый `library-index.json` игнорируется, индекс пересобирается в фоне пулом до 8 воркеров. Файл кэша можно удалить в любой момент.
3. `flac-quality.json` создаётся лениво при первой проверке; битый/старый файл игнорируется.
4. `_old` создаётся только при первом успешном обновлении; старые файлы не удаляются.
5. Откат: выключить `FLAC_MONITOR`, игнорировать журнал; `_old` можно вернуть вручную. Спеки и код остаются, данные не мигрируют.
6. Документация: `.env.example`, `docs/` (новый параметр, `_old`, ограничение «только при открытом окне»), `CHANGELOG.md` в `[Unreleased]`.
