# Spec Delta

## MODIFIED Requirements

### Requirement: Скачивание трека по ссылке

Приложение MUST принимать ссылку вида `music.yandex.ru/album/{albumId}/track/{trackId}`, ссылку вида `music.yandex.(ru|com|kz|by|uz)/album/{albumId}` (без trackId), ссылку вида `music.yandex.(ru|com|kz|by|uz)/playlists/{uuid}` (включая префиксы вида `lk.<uuid>`, `ps.<uuid>` и query-хвосты), а также несколько ссылок в одном вводе (разделённые переносом строки, пробелом или запятой). Приложение MUST скачивать аудио в `OUTPUT_DIR` (по умолчанию `./downloads`). В логе статусы MUST использовать технические токены, а в строке трека MUST отображаться человекочитаемый статус, соответствующий токену.

#### Scenario: Вставил ссылку — получил файл

- **WHEN** пользователь вставляет ссылку на трек и нажимает «Скачать»
- **THEN** в логе появляется `[downloading] Artist — Title`, а после завершения — `[done] Artist — Title (FLAC|MP3)`

#### Scenario: Файл уже есть

- **WHEN** целевой файл уже существует в папке назначения
- **THEN** скачивание пропускается и в логе появляется `[skip] Artist — Title (already exists)`

#### Scenario: Вставил ссылку на плейлист — получил файлы

- **WHEN** пользователь вставляет ссылку вида `music.yandex.by/playlists/{uuid}` и нажимает «Скачать»
- **THEN** появляется заголовок `[playlist] Название (N треков)` и ровно по одной строке на каждый уникальный трек (в порядке плейлиста, со статусом «Ожидание», которому в логе соответствует `[queued]`), а в конце — `[finished] X ok, Y skip, Z error`

#### Scenario: Вставил ссылку на альбом — получил файлы

- **WHEN** пользователь вставляет ссылку вида `music.yandex.ru/album/{albumId}` и нажимает «Скачать»
- **THEN** приложение резолвит альбом в список треков и скачивает их тем же способом, что и плейлист: заголовок `[album] Название (N треков)`, по одной строке на каждый трек, общий прогресс, итоговая строка `[finished] X ok, Y skip, Z error`

#### Scenario: Одна строка на трек

- **WHEN** трек плейлиста или альбома качается и завершается
- **THEN** его строка обновляется на месте («Ожидание» -> «Скачивается» -> «Готово - FLAC|MP3» с цветом), новые строки на каждое событие НЕ добавляются; строка пропуска показывает «Пропущено - уже есть|дубль|недоступно», строка ошибки — «Ошибка» с причиной; в логе этим состояниям соответствуют `[queued]`, `[downloading]`, `[done]`, `[skip]` и `[error]`

#### Scenario: Плейлист с query-хвостом и префиксом

- **WHEN** ссылка имеет вид `music.yandex.ru/playlists/lk.<uuid>?utm_source=web`
- **THEN** приложение принимает ее как плейлист и резолвит тот же набор треков, что и без префикса и хвоста

#### Scenario: Несколько ссылок разом

- **WHEN** пользователь вставляет в поле ввода несколько ссылок (разделённые переносом строки, пробелом или запятой), нажимает «Скачать»
- **THEN** приложение обрабатывает каждую ссылку по очереди, применяя соответствующий пайплайн для каждого (альбом/плейлист/трек). Если одна из ссылок некорректна — она пропускается с `[error]`, остальные обрабатываются дальше.

### Requirement: Пакетное скачивание плейлиста

Приложение MUST скачивать треки плейлиста и альбома пулом параллельных воркеров с настраиваемым числом (`PLAYLIST_WORKERS` в `.env`: целое 1..10, по умолчанию 3), при этом каждый трек MUST проходить стандартный пайплайн (FLAC first с MP3-fallback, обязательные теги, потоковая запись, атомарная публикация `temp → rename`). Ошибка или недоступность одного трека MUST NOT останавливать остальные. Повтор одного и того же ID внутри плейлиста/альбома MUST скачиваться один раз, повторные вхождения пропускаются как уже обработанные.

#### Scenario: Пачка из нескольких треков

- **WHEN** плейлист или альбом содержит 5 уникальных доступных треков
- **THEN** все 5 файлов появляются в `downloads/` с тегами, 5 строк треков переходят в «Готово - FLAC|MP3», а финал — `[finished] 5 ok, 0 skip, 0 error`

#### Scenario: Недоступный трек пропускается

- **WHEN** трек плейлиста или альбома недоступен (`available=false`, нет прав, 403/404)
- **THEN** строка трека показывает «Пропущено - недоступно» (`[skip] (unavailable)` в логе), остальные треки качаются дальше, счетчик `skip` в финале увеличивается

#### Scenario: Дубль качается один раз

- **WHEN** один и тот же ID встречается в плейлисте или альбоме дважды
- **THEN** файл скачивается один раз, строка трека показывает «Пропущено - дубль» (`[skip] (duplicate)` в логе), повторной записи файла нет

#### Scenario: Ошибка одного не роняет пачку

- **WHEN** один трек завершается ошибкой сети или тегирования
- **THEN** строка трека показывает «Ошибка» с причиной (`[error]` в логе), остальные треки продолжают качаться, финал учитывает ошибку в счетчике `error`

#### Scenario: Число воркеров настраивается

- **WHEN** в `.env` задано `PLAYLIST_WORKERS=10`
- **THEN** до 10 треков качаются параллельно

#### Scenario: Мусор в настройке воркеров

- **WHEN** `PLAYLIST_WORKERS` отсутствует, не число или вне диапазона 1..10
- **THEN** приложение использует значение по умолчанию 3 и работает как обычно

### Requirement: Агрегированный статусбар прогресса

Во время каждой загрузки («job'ы») приложение MUST показывать полосу прогресса на всю ширину окна между строкой ввода и списком треков. Статусбар MUST показывать общий процент, счётчик треков (`завершено/всего`) и суммарные байты, когда размеры известны. Общий процент MUST вычисляться как `(завершённые треки + суммы долей активных) / всего треков`, чтобы знаменатель был стабилен с момента старта и процент не прыгал при неизвестных размерах файлов. Для одиночного трека job'а состоит из одного трека: его прогресс (проценты и байты) MUST отображаться и в статусбаре, и в его строке — как и у треков плейлиста. Обновления статусбара MUST идти с той же частотой, что и прогресс треков (троттлинг ~200 мс). До первой загрузки статусбар MUST NOT отображаться. После завершения job'ы MUST показываться итоговая сводка (см. capability `desktop-app`), а полоса прогресса MAY быть скрыта; остановленная пользователем job'а MUST остаться на фактическом проценте с итогом «остановлено».

#### Scenario: Плейлист из 20 треков

- **WHEN** качается плейлист из 20 треков, завершено 10, ещё 2 качаются
- **THEN** статусбар показывает `55%`, `10/20 треков` и суммарные байты (при известных размерах), значение процента растёт плавно и не прыгает назад

#### Scenario: Одиночный трек с процентами

- **WHEN** пользователь вставил ссылку на один трек с известным размером
- **THEN** статусбар и строка трека показывают живые проценты и байты, после завершения — 100% и статус «Готово»

#### Scenario: Неизвестный размер файла

- **WHEN** сервер не отдал размер файла
- **THEN** статусбар показывает проценты по трекам (доля завершённых), а байты — только если хотя бы у части треков размер известен; отсутствие размера не ломает полосу

#### Scenario: Ошибка одного трека не роняет статусбар

- **WHEN** один из треков плейлиста завершился ошибкой
- **THEN** статусбар продолжает показывать общий прогресс остальных, итоговая строка `[finished]` учитывает ошибку как раньше

#### Scenario: Между загрузками

- **WHEN** предыдущая загрузка завершена и новая ещё не начата
- **THEN** итоговая сводка предыдущей загрузки остаётся видимой, а полоса прогресса скрыта до старта новой job'ы

#### Scenario: До первой загрузки

- **WHEN** приложение запущено и ни одной загрузки ещё не было
- **THEN** статусбар не отображается; виден экран ожидания с полем ввода и подсказкой

#### Scenario: Остановка замораживает статусбар

- **WHEN** пользователь останавливает активную загрузку, дойдя до 40%
- **THEN** статусбар остаётся на фактическом проценте (не доводится до 100%) с итогом «N/M треков, остановлено», частично скачанные треки не считаются завершёнными
