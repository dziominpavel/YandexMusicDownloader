## Context

См. proposal.md — Why. Технический контекст:

- Фронтенд — один `src/frontend/dist/index.html` (vanilla JS, Wails runtime events). События: `log`, `playlist-start`, `tracks`, `track-status`, `progress`.
- Прогресс уже есть для плейлиста (`progress.go` — троттлинг 200 мс, `Progress{TrackID, Done, Total, Percent}`), но `ui.App.Download` вызывает `DownloadTrack(..., nil)` — одиночный трек прогресса не имеет; событие жизненного цикла есть только `playlist-start`.
- Конфиг: `config.Load` читает `.env` рядом с exe один раз в `NewApp()`; `EMBED_COVER` (дефолт `true`) читается и уходит в `tagger.Adapter`, `FORMAT` не читается никем.
- `App` уже имеет мьютекс `mu` для emission событий и `logSink`/`confirm` подмены для тестов.

## Goals / Non-Goals

**Goals:**

- Агрегированный статусбар для любой загрузки (1 трек или плейлист) + сохранение существующих per-track строк.
- Окно настроек, редактирующее `.env`, с горячим применением без перезапуска.
- Подключить в окно настроек поддерживаемые параметры: `EMBED_COVER` (ключ уже читается, дефолт `true`), `FORMAT` — убрать как мёртвый.
- Остановка активной загрузки одной кнопкой (кнопка «Скачать» становится «■ Остановить»).

**Non-Goals:**

- Новый формат хранения настроек (`settings.json`) — остаёмся на `.env`.
- Настройки, которых нет в коде: выбор формата (FLAC-first захардкожен спекой), битрейт, переименование шаблонов.
- Пауза с продолжением (resume) — только полная остановка job'ы (см. D8).
- Изменение логики воркеров, дедупликации, тегирования.

## Decisions

### D1. Агрегация прогресса — на фронтенде

Все данные (`track-status`, `progress`, `playlist-start`/`job-start`) уже приходят в JS. Считать `(завершённые + суммы долей активных) / N` в Go — значит дублировать состояние и добавлять ещё одно событие. **Решение:** JS держит карту `job = {total, states: Map<trackId, {pct, done, total, doneFlag}>}` и рисует статусбар из неё.

Альтернатива (отклонена): событие `job-progress` из Go — больше кода в бэкенде, состояние всё равно надо сверять с событиями строк.

Формула `% = (doneCount + Σ activeShare) / total`, где `activeShare = pct/100` (при `pct = -1` → 0). Знаменатель константен с момента `job-start`. Байты — вторая подпись, суммируются `Done`/`Total` только известные (`Total > 0`), при неизвестных размерах строка байтов скрыта.

### D2. Жизненный цикл — событие `job-start(title, count)`

`playlist-start(title, count)` уже есть; для одиночного трека нужен тот же сигнал. **Решение:** ввести `job-start` с теми же полями (для плейлиста title = «[playlist] Название», для одиночного — label трека), фронтенд очищает предыдущий job и строит строки. `playlist-start` перестаёт эмититься (фронтенд слушает только `job-start`) — в бэкенде это одна строка в `downloadPlaylist` и новая в `Download`.

Альтернатива (отклонена): переиспользовать `playlist-start` и для одиночного — собьёт смысл «[playlist]» в заголовке и оставит мёртвую ветку в JS.

Окончание job'ы: сейчас `[finished]` / `[done]` в логе триггерят очистку. **Решение:** ввести событие `job-end(summary)` (ok/skip/error counts), статусбар замирает на итоге; лог остаётся как есть (спека требует `[finished]`).

### D3. Одиночный трек — те же события, что и трек плейлиста

В `Download()` одиночного трека: эмитить `job-start(label, 1)`, `track-status` (из уже существующего `formatTrackStatus`), реальный `onProgress` → `progress`. Общий код выносится в маленький помощник (например, `runJob`), чтобы плейлист и одиночный трек не расходились. Лог для одиночного трека сохраняет текущее поведение (`[downloading]`/`[done]` в логе) — спека `desktop-app` требует этих строк.

### D4. Настройки — модалка в том же `index.html`, бэкенд-биндинги в `ui.App`

Окно настроек — overlay-модалка (позиционирование `fixed`), без отдельного Wails-окна: проще, всё в одном HTML, русские тексти легко держать. Кнопка ⚙/«Настройки» справа от «Скачать», дизейблится вместе с ней на время `Download` (фронтенд уже дизейблит `#dl`; расширить на кнопку настроек + блокировку из бэкенда по факту активной job'ы).

Бэкенд-биндинги (`Bind: []any{app}`): `GetSettings()` → текущие значения, `CheckToken(token)` → результат `config.Validate`, `SaveSettings(patch)` → валидация → запись `.env` → хот-релоад.

### D5. Хранение — `.env` как единственный источник, редактируется построчно

`config.Write(path, updates map[string]string)`: читает файл, для каждого известного ключа заменяет строку `KEY=VALUE` (сохраняя комментарии и порядок), отсутствующие ключи добавляет в конец, незнакомые строки не трогает. Не переписывает файл целиком → ручные правки и комментарии переживают сохранение из UI.

Альтернатива (отклонена): `settings.json` — второй источник правды, правило приоритета, правка спек (`desktop-app`: «токен из `.env`»).

Ошибки: файл недоступен на запись → ошибка на русском, состояние в памяти не меняется (сначала пишем файл, потом применяем).

### D6. Хот-релоад — переиспользовать конструктор

Выделить из `NewApp` функцию `apply(cfg config.Config) error`: валидация токена → `downloader.NewClient` → `ConvertM4A`/`PlaylistWorkers`/`Tag`/`OnPublished` → `setupLibrary`. `NewApp` = `Load` + `apply`; `SaveSettings` = `Write` + `apply`. Тот же код, две точки входа, нет расхождений.

`EMBED_COVER`: `config.Config.EmbedCover bool` (дефолт `true`, off-список `0/false/no/off`), `tagger.Adapter(cfg.EmbedCover)`.

### D7. Блокировка настроек на время скачивания

Бэкенд знает активную job'у (флаг в `App`, поднимается в `Download`, опускается по завершении). `SaveSettings`/`GetSettings` возвращают ошибку «скачивание идёт»; фронтенд дополнительно дизейбит кнопку. Двойная защита: даже если JS-дизейбл проскочит, бэкенд не применит конфиг посреди пулa воркеров.

### D8. Остановка — через контекст запросов, кнопка трансформируется

Кнопка «Скачать» на время job'ы не дизейблится, а меняет назначение: красная «■ Остановить» (потом «Останавливаю…»). Одна кнопка вместо второй — место в строке не меняется, состояние очевидно.

**Реализация:** `downloader.Client` получает контекст job'ы (`StartJob()` на старте `Download`, `Stop()` по кнопке); `newRequest` строит запрос через `http.NewRequestWithContext`, поэтому остановка обрывает уже идущую передачу сразу, а не после таймаута. Флаг `Stopped()` дополнительно проверяется в пайплайне и перед запуском каждого трека пула: не начатые треки получают `KindStopped` (`[stopped]`) и счётчик `Summary.Stopped`, а не `[error]`. Остановленная job'а шлёт `job-end(..., stopped=true)` — фронтенд НЕ дотягивает доли до 100%, полоса замораживается на фактическом проценте (янтарный класс `stopped`). Сброс — `StartJob()` в начале каждой новой `Download`.

Альтернатива (отклонена): `context` внутрь каждой сигнатуры пайплайна — правит все вызовы и тесты; пауза с продолжением — другой уровень сложности (сохранение позиции, возобновление очереди), вне этой job'ы.

## Risks / Trade-offs

- [`.env` рядом с exe может быть не записываемым (Program Files)] → ошибка видна в UI, приложение продолжает работать со старым конфигом; миграция файла не требуется.
- [Горячая смена `OUTPUT_DIR`/`LIBRARY_DIR` во время индексации] → `SaveSettings` блокируется также на время `index.Refresh` (или дожидается завершения — в design закладываем: индексация не блокирует сохранение, новый `setupLibrary` заменяет указатель, старая горутина дорабатывает на своём объекте; кэш-файл общий — риск минимален, проверять тестом).
- [Фронтенд-агрегация рассинхронизируется с бэкендом] → агрегат — чисто display-слой; истина в `[finished]`/`job-end`, расхождение худшее — неверный процент на полосе, не поведение.
- [Модалка настроек поверх лога ломает существующий CSS] → минимальный overlay с собственным контейнером, стили рядом с существующими; проверять вручную.
- [Потеря комментариев в `.env` при записи] → построчная правка вместо регенерации; покрыть тестом `config_test` (файл с комментариями + чужой ключ).
- [Событие `job-start` сломает старый фронтенд] → фронтенд и бэкенд поставляются одним exe, версии не разъезжаются.

## Migration Plan

Миграции нет: `.env` формат не меняется (только убирается мёртвый `FORMAT` из `.env.example` — на работающие системы не влияет). Откат = откат коммитов.
