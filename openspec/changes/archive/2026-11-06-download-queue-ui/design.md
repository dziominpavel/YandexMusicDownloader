# Design

## Context

Сейчас скачивание — это одна блокирующая job'а: `App.Download` вызывается из окна и не возвращается до конца, фронтенд ведёт единственную `job`-модель (`job-start` → `tracks` → `track-status`/`progress` → `job-end`), а пул воркеров создаётся внутри `DownloadPlaylist` на одну ссылку. `Client.StartJob` вызывается перед каждой ссылкой и отменяет контекст предыдущей, `Stop` отменяет клиент целиком. Настройки пересоздают клиент и индекс через `apply`. Всё это описано в proposal.md — здесь только то, что влияет на реализацию.

Ограничения: Wails v2 (биндинги синхронные, события — единственный канал в UI), один exe, новые зависимости не добавляем, `.env`-ключи не меняем, `PLAYLIST_WORKERS` получает новый смысл «параллельных задач на всю очередь».

## Goals / Non-Goals

**Goals:**

- Плоская очередь задач (трек = задача), общий пул `PLAYLIST_WORKERS`, ожидание слота, отмена/повтор по задаче.
- Один источник истины очереди в Go; фронтенд только отображает состояние и отправляет команды.
- Одна поверхность «Очередь» + журнал; ввод всегда доступен.
- Дубли решаются в строке, не блокируя остальные задачи.
- Сохранить без изменений пайплайн загрузки, тегирование, индексацию, ретраи и формат лога.

**Non-Goals:**

- Сохранение и восстановление очереди между запусками.
- Вложенные группы (альбом как сворачиваемая группа) — выбран плоский список.
- Уведомления в трее, история ссылок, переработка окна настроек и мониторинга FLAC.
- Новые `.env`-ключи и новые зависимости.

## Decisions

### D1. Очередь живёт в Go, фронтенд — тонкий рендер

Новый пакет `internal/queue` владеет списком задач, пулом и состояниями; `internal/ui` превращает его события в Wails-события и биндинги. Альтернатива — оставить оркестрацию в JS и вызывать `Download` на каждую ссылку параллельно — отклонена: события глобальны и склеят задачи разных job'ов, отмена одной задачи невозможна, пересоздание клиента в настройках ломает чужие загрузки.

Биндинги: `Submit(links)`, `CancelTask(key)`, `RetryTask(key)`, `CancelAll()`, `ClearFinished()`, `ResolveDuplicate(key, accept)`, `GetQueue()`. `Download` и `Stop` удаляются; `GetQueue` нужен для первого кадра и для случаев, когда окно перерисовалось.

### D2. Задача — трек, источник — метаданные

Плоский список задач. У каждой задачи есть `key` (монотонный id, уникален даже для одного TrackID), `trackId` (для дедупа), `sourceKey`/`sourceLabel`/`sourceOrder`, `state`, `pct`, `done`, `total`, `format`, `reason`, `path`. Ссылка порождает одну задачу `resolving` (строка «определяется»), которая после резолва заменяется задачами треков в порядке источника. Источники показываются чипами с фильтром и «отменить источник».

Альтернатива — задача = ссылка с вложенными треками — отклонена пользователем: плоский список даёт управление каждым треком и одинаковую разметку строки.

### D3. Единый семафор и порядок

Один семафор размера `Workers` на всё приложение; резолв ссылок идёт отдельным маленьким пулом (2 параллельно), чтобы «определяется» не занимал слот загрузки. Порядок FIFO по `sourceOrder` + позиции в источнике; повтор задачи встаёт в конец очереди. Шлюз пула перечитывает `Workers` при каждом запуске задачи, поэтому новое значение из настроек действует без перезапуска.

Альтернатива — пул на источник — даёт невидимое превышение лимита при нескольких ссылках и ломает счётчик «N потоков».

### D4. Контекст: на задачу, а не на процесс

`Stop`/`StartJob` в нынешнем виде мешают параллельности: `StartJob` отменяет предыдущий контекст. Вводим `runCtx` (создаётся при старте очереди, отменяется `CancelAll`) и `taskCtx`, производный от него. В `downloader` добавляются варианты с контекстом: `DownloadTrackCtx`, `ResolveTrackCtx`, `AlbumCtx`, `PlaylistCtx`, а внутренние `newRequest`/`Get` принимают `ctx`. Старые методы остаются обёртками с `context.Background()` для тестов и мониторинга FLAC. `Client.Stop` сохраняется как «отменить run», но планировщик отменяет задачи сам.

### D5. События и троттлинг

Канал в UI: `task-added`, `task-updated` (state/pct/bytes/format/reason), `task-removed`, `queue-updated` (агрегат), `sources-updated`, `log`. Прогресс задачи троттлится в `downloader` как сейчас (~200 мс), агрегат очереди — отдельный троттлинг ~250 мс, чтобы 10 параллельных задач не давали 50 событий в секунду. Фронтенд коалесцирует отрисовку через `requestAnimationFrame` (уже есть в текущем статусбаре).

Альтернатива — отправлять снапшот всей очереди на каждое изменение — проще для фронтенда, но гоняет килобайты JSON на каждый процент; оставляем только для `GetQueue` и для `queue-updated` с агрегатом.

### D6. Дубли — состояние задачи, а не модалка

Проверка дублей (`checkDuplicate`) выполняется перед запуском задачи в воркере; при совпадении задача переходит в `needs-review` и ждёт ответа по своему `key`. Остальные задачи идут дальше. В строке показываются процент, имя и полный путь (перенос по символам, копирование), при другом формате — предупреждение. Один канал ответа на задачу, никакого общего «одного промпта»: прежний `dupReply`-мьютекс удаляется.

Отказ от модалки — сознательное изменение спеки: иначе несколько одновременных кандидатов теряются (сейчас второй промпт молча пропускается) и фокус уходит из поля ввода.

### D7. Фронтенд: модель задач вместо job

`tasks: Map<key, taskView>` + порядок добавления; строка обновляется на месте по `task-updated`. `jobReset`/`handleJobStart`/`handleJobEnd` удаляются; `state` экрана вычисляется из очереди (`empty` / `working` / `settled`). Журнал (`#log`) получает события `log` без очистки при новой задаче; очистка — кнопкой. Составные ключи убирают коллизию одного TrackID в двух источниках.

`window.__yamdl` остаётся тестовым фасадом, но его методы меняются на очередь (`getTasks`, `submit`, `cancelTask`); стенд переписывается.

### D8. Компоновка и прокрутка

`.app-shell` — `height: 100vh`, колонка: заголовок, закреплённая форма, сводка очереди, прокручиваемая область задач (`flex: 1; min-height: 0`), журнал. В режиме «очередь не пуста» форма сворачивается (скрываются заголовок и подсказка), чтобы на 860×600 оставалось место списку. Строки создаются инкрементально, без виртуализации в первой версии; «Очистить завершённые» убирает терминальные строки.

Альтернатива — двухколоночный layout с деталями справа — отклонена: при 860 px ширины места нет, а приложение остаётся списком загрузок.

### D9. Обновление FLAC — источник в очереди

`DownloadFound` больше не запускает отдельную job'у: выбранные элементы становятся задачами источника `flac-update`. Из `quality.Upgrader` выделяется запуск одной задачи (`UpgradeItem(ctx, item, emit, progress)`), чтобы семафор очереди оставался единственным ограничителем; внутренний пул `Workers: 2` уходит. Проверка `CheckQuality` остаётся отдельной функцией и в очередь не попадает.

### D10. Настройки во время очереди

`SaveSettings` по-прежнему пишет `.env` и вызывает `apply`, но задачи захватывают клиент и каталог назначения в момент запуска (или постановки) — активные продолжают со старыми параметрами, новые берут новые. Токен: старый клиент доживает свои запросы, новый обслуживает новые задачи; `tokenGen` уже защищает от гонки проверки. Блокировки `isBusy` в `GetSettings`/`SaveSettings`/`DownloadFound` удаляются.

Риск: `apply` пересобирает индекс, а старый клиент публикует файлы в старый индекс; новый индекс увидит их при следующем обновлении. Приемлемо, отмечаем в рисках.

### D11. Тесты

Go: юнит-тесты планировщика на фейковом раннере (порядок, лимит, отмена, повтор, дедуп, дубли), тесты контекста в `downloader`, обновлённые тесты `internal/ui` (события и биндинги). JS: `tests/statusbar_check.js` переписывается в `tests/queue_check.js` (тот же VM-подход), обновляются `tests/quality_check.js`, `tests/settings_check.js`, `docs/16-ui-design.md`, README со ссылкой на стенд.

## Risks / Trade-offs

- **Шквал событий при 10 параллельных задачах** → троттлинг прогресса 200 мс и агрегата 250 мс, коалесцирование кадров; строки обновляются только по видимым полям.
- **Гонка «отмена vs завершение»** → отмена и финализация под мьютексом задачи; если задача уже опубликовала файл, она остаётся «готово» и отмена игнорируется (документируем).
- **Одинаковый трек из двух источников** → дедуп по `trackId` при постановке; разные треки с одинаковым именем файла по-прежнему разрешаются через существующий `ErrAlreadyExists`.
- **`PLAYLIST_WORKERS` меняет смысл** (было «на плейлист», стало «на очередь») → при значении 10 несколько ссылок теперь дают 10 параллельных загрузок и большее давление на API; значение по умолчанию 3 сохраняется, риск упомянуть в CHANGELOG.
- **Пересборка индекса при сохранении настроек** → активный клиент публикует в старый индекс; новые файлы попадут в него при следующем сканировании.
- **Удаление `Download`/`Stop` ломает существующие тесты и стенды** → менять их в том же change, иначе сборка красная; задачи сгруппированы по фазам.
- **Долгий журнал и список** → журнал уже ограничен 500 строками; список очищается кнопкой, память сессии ограничена.

## Migration Plan

Приложение локальное, состояние не персистится: очередь начинается пустой, `.env` и существующие файлы не меняются. Откат — вернуть предыдущий exe; недокачанные файлы удаляются штатным механизмом временных файлов. Версия проекта не меняется, пользовательский пункт добавляется в `## [Unreleased]` CHANGELOG.
