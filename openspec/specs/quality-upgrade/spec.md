# quality-upgrade Specification

## Purpose

Мониторинг коллекции на треки без lossless: сопоставление локальных файлов с Яндекс Музыкой по ID или исполнителю/названию, проверка появления FLAC, предложение пользователю и обновление файла на месте с сохранением старого в `_old`.

## Requirements

### Requirement: Охват и кандидаты

Приложение MUST проверять аудиофайлы в `LIBRARY_DIR` и `OUTPUT_DIR` рекурсивно. Кандидатами MUST считаться только `.mp3`; `.flac` и `.m4a` MUST пропускаться (FLAC уже lossless, M4A — вне v1). Каталоги `_old` MUST исключаться. Файлы вне этих корней MUST NOT проверяться.

#### Scenario: Обе папки проверяются

- **WHEN** `LIBRARY_DIR=F:\Music`, `OUTPUT_DIR=downloads` и мониторинг включён
- **THEN** проверка рассматривает MP3 из обеих папок, включая подкаталоги

#### Scenario: Уже lossless или вне v1

- **WHEN** файл имеет расширение `.flac` или `.m4a`
- **THEN** он не попадает в список кандидатов и не предлагается к обновлению

#### Scenario: Старое в _old

- **WHEN** MP3 лежит в `LIBRARY_DIR\_old` или `OUTPUT_DIR\_old`
- **THEN** он не проверяется и не участвует в проверке дублей

### Requirement: Сопоставление с треком Яндекса

Приложение MUST сначала использовать Yandex ID из тегов (`YANDEX_TRACK_ID`, UFID или source-url). Если ID отсутствует, приложение MUST искать трек через `/search` по исполнителю и названию и сравнивать нормализованные значения; поисковое совпадение MUST предлагаться только при высоком совпадении и MUST NOT скачиваться без подтверждения. Файлы без ID и без пригодных исполнителя и названия MUST пропускаться.

#### Scenario: ID есть

- **WHEN** в тегах файла найден Yandex ID
- **THEN** приложение проверяет lossless для этого ID и не выполняет поиск по названию

#### Scenario: ID нет — поиск по названию

- **WHEN** ID отсутствует, а теги или имя файла дают исполнителя и название
- **THEN** приложение ищет трек через `/search` и показывает найденного кандидата с исполнителем, названием, альбомом, годом и процентом совпадения

#### Scenario: Уверенного совпадения нет

- **WHEN** поиск не дал кандидата выше порога
- **THEN** файл пропускается без окна и без скачивания

#### Scenario: Нет ни ID, ни тегов, ни осмысленного имени

- **WHEN** файл называется `track001`, не имеет тегов и Yandex ID
- **THEN** файл не участвует в поиске и не даёт ложного предложения

### Requirement: Проверка доступности lossless

Приложение MUST проверять lossless через `get-file-info` с `quality=lossless` и MUST определять результат по `codec`: `flac`/`flac-mp4` — доступен, `mp3`/`aac-mp4` — нет. Запросы MUST быть троттлированы. Сетевые ошибки и 429 MUST NOT портить журнал.

#### Scenario: FLAC доступен

- **WHEN** сервер вернул `codec=flac` или `codec=flac-mp4`
- **THEN** трек попадает в список найденного и предлагается к обновлению

#### Scenario: FLAC нет

- **WHEN** сервер вернул `codec=mp3` или `codec=aac-mp4`
- **THEN** трек не предлагается, а в журнале сохраняется статус «FLAC нет» со сроком следующей проверки

#### Scenario: Временная ошибка

- **WHEN** запрос завершился сетевой ошибкой или 429
- **THEN** приложение делает ограниченное число повторов, а при неудаче сохраняет ошибку с коротким TTL, не выдавая её за «FLAC нет»

### Requirement: Ответы доступа при проверке

Ответы `smart_preview`/`preview` и 401 MUST останавливать проверку с сообщением о токене. 403 MUST помечать конкретный трек недоступным и не останавливать остальные, но серия из 3 подряд MUST останавливать проверку. Такие ответы MUST NOT помечать треки как «FLAC нет».

#### Scenario: Токен не даёт полный доступ

- **WHEN** сервер вернул `quality=smart_preview` или `quality=preview`
- **THEN** проверка останавливается с сообщением проверить токен и подписку, а треки не помечаются как «FLAC нет»

#### Scenario: Токен не принят

- **WHEN** `get-file-info` вернул 401
- **THEN** проверка останавливается с сообщением о токене, журнал не обновляется массово

#### Scenario: Доступ к одному треку запрещён

- **WHEN** `get-file-info` вернул 403 для одного трека
- **THEN** трек помечается недоступным с длинным TTL, проверка продолжает остальные треки

#### Scenario: Серия 403

- **WHEN** `get-file-info` вернул 403 три раза подряд
- **THEN** проверка останавливается с сообщением о правах, чтобы не помечать всю коллекцию недоступной

### Requirement: Журнал проверок

Приложение MUST хранить журнал рядом с exe: track ID, кодек, статус, время проверки и срок следующей. «FLAC нет» MUST перепроверяться не чаще раза в 30 дней, ошибки — по короткому TTL, недоступные — по длинному. При смене `accountUID` или переходе `hasPlus` с false на true журнал MUST сбрасываться. Отклонённые поисковые совпадения MUST храниться для локального файла списком вместе с метаданными найденного трека, MUST NOT истекать автоматически и MUST NOT предлагаться снова до явной отмены. При обновлении схемы журнала ранее сохранённые отклонения MUST сохраняться.

#### Scenario: Повторный запуск в пределах TTL

- **WHEN** трек уже проверен и срок следующей проверки не наступил
- **THEN** приложение не делает повторный запрос и не показывает трек

#### Scenario: Сменился аккаунт

- **WHEN** `accountUID` в журнале отличается от текущего
- **THEN** журнал сбрасывается и все кандидаты проверяются заново

#### Scenario: Появился Плюс

- **WHEN** у того же аккаунта `hasPlus` изменился с false на true
- **THEN** записи «FLAC нет» сбрасываются и треки проверяются заново

#### Scenario: Поисковое совпадение отклонено

- **WHEN** пользователь нажал «Не тот трек» у поискового совпадения
- **THEN** это совпадение запоминается и не предлагается снова до явного возврата

#### Scenario: Отклонение переживает перезапуск

- **WHEN** приложение перезапущено после отклонения поискового совпадения
- **THEN** сохранённые отклонения остаются активными и не предлагаются снова

#### Scenario: Отклонение не истекает

- **WHEN** после отклонения прошло больше 180 дней
- **THEN** отклонённое совпадение всё ещё не предлагается, пока пользователь не вернёт его

#### Scenario: Старый журнал мигрирует

- **WHEN** приложение загружает журнал версии 1 с непустым `declined`
- **THEN** сохранённые отклонения переносятся в журнал версии 2 и остаются активными

### Requirement: Время последней проверки

Приложение MUST сохранять время последней завершённой проверки и её результат (найдено N / ничего не найдено / ошибка) и MUST обновлять их после каждой проверки. Эти данные MUST быть доступны окну настроек и бейджу на кнопке «Настройки» без повторного запроса к API и MUST сохраняться между запусками. После завершения проверки индикация MUST показывать фактический результат, а не состояние выполнения.

#### Scenario: Проверка завершилась

- **WHEN** проверка завершилась и нашла 3 трека
- **THEN** в журнале сохраняются время завершения и результат «найдено 3», которые показывают настройки и бейдж

#### Scenario: Приложение перезапущено

- **WHEN** приложение запущено после проверки
- **THEN** настройки показывают сохранённые время и результат без новой проверки

#### Scenario: Проверка завершилась ошибкой

- **WHEN** проверка остановилась из-за токена, прав или сети
- **THEN** сохраняются время попытки и результат «ошибка», а причина доступна в логе

#### Scenario: Индикация не остаётся в состоянии выполнения

- **WHEN** проверка завершилась без находок
- **THEN** индикация показывает «ничего не найдено», а не «проверка идёт»

### Requirement: Триггеры проверки

Приложение MUST иметь настройку `FLAC_MONITOR` (по умолчанию выключена) и ручную команду «Проверить сейчас» в разделе мониторинга окна настроек. При включённой настройке проверка MUST запускаться при старте, если с последней прошло не менее 7 дней, и раз в 7 дней, пока окно открыто. При закрытом приложении проверок нет. Если токен пуст/невалиден или нет Плюса, проверка MUST завершаться сообщением и MUST NOT создавать ложных статусов.

#### Scenario: Ручная проверка

- **WHEN** пользователь нажал «Проверить сейчас» в настройках
- **THEN** проверка запускается независимо от значения `FLAC_MONITOR`

#### Scenario: Автопроверка на старте

- **WHEN** `FLAC_MONITOR=true` и с последней успешной проверки прошло 7 дней
- **THEN** после готовности индекса запускается проверка в фоне, не блокируя окно

#### Scenario: Срок не наступил

- **WHEN** `FLAC_MONITOR=true` и последняя проверка была вчера
- **THEN** проверка не запускается и в лог не пишется лишних строк

#### Scenario: Нет Плюса

- **WHEN** токен валиден, но у аккаунта нет Плюса
- **THEN** проверка завершается сообщением, что lossless недоступен для аккаунта, и не помечает треки как «FLAC нет»

### Requirement: Окно найденного

При находке приложение MUST сохранить список и показать бейдж количества на кнопке «Настройки»; окно MUST открываться из настроек. Окно MUST показывать локальный файл, текущий и найденный форматы и папку назначения нового FLAC (`OUTPUT_DIR`); для поисковых совпадений — найденный трек, альбом, год и процент. ID-совпадения MUST быть предвыбраны, поисковые — только при уверенном совпадении. Для каждого поискового совпадения MUST быть действие «Не тот трек», которое убирает строку из текущего списка и сохраняет отклонение без скачивания; для ID-совпадений это действие MUST NOT показываться. После отклонения сводка и бейдж MUST обновляться, а если строк не осталось — окно MUST закрываться. Действия: «Скачать все», «Показать список», «Позже». «Позже» MUST сохранять список и бейдж; при отсутствии находок окно MUST NOT показываться.

#### Scenario: Много ID-совпадений

- **WHEN** проверка нашла 67 треков по ID
- **THEN** окно показывает сводку «Найдено 67 треков», все предвыбраны, доступны «Скачать все» и «Показать список»

#### Scenario: Поисковые совпадения

- **WHEN** найдены треки без ID
- **THEN** они показаны отдельно с найденным треком, альбомом, годом и процентом; предвыбраны только уверенные совпадения

#### Scenario: Ничего не найдено

- **WHEN** проверка не нашла ни одного lossless-варианта
- **THEN** окно не показывается, в логе остаётся итоговая строка проверки

#### Scenario: Позже

- **WHEN** пользователь нажал «Позже»
- **THEN** окно закрывается, найденное сохраняется, а на кнопке «Настройки» остаётся бейдж с количеством

#### Scenario: Открытие из настроек

- **WHEN** есть найденные треки, пользователь открыл настройки и нажал «Открыть найденное»
- **THEN** открывается окно со сводкой и списком

#### Scenario: Папка назначения видна

- **WHEN** в списке есть MP3 из папки коллекции
- **THEN** окно показывает, что новый FLAC будет скачан в `OUTPUT_DIR`, а старый MP3 перемещён в `_old`

#### Scenario: Отклонение в окне

- **WHEN** пользователь нажал «Не тот трек» у поискового совпадения
- **THEN** строка исчезает из списка, файл не скачивается, отклонение сохраняется, а бейдж уменьшается на единицу

#### Scenario: Последнее совпадение отклонено

- **WHEN** пользователь отклонил единственное оставшееся поисковое совпадение
- **THEN** окно закрывается, а бейдж скрывается

#### Scenario: ID-совпадение не отклоняется

- **WHEN** найденный элемент получен по Yandex ID
- **THEN** действие «Не тот трек» для него не показывается

### Requirement: Обновление файла

По подтверждению приложение MUST скачать lossless в `OUTPUT_DIR` (с учётом `SUBDIRS` и обычного имени `Исполнитель - Название.ext`), при `flac-mp4` конвертировать в FLAC, если ffmpeg доступен, иначе сохранить lossless `.m4a`, записать теги и атомарно опубликовать. Новый аудиофайл MUST NOT попадать в `LIBRARY_DIR`. Только после успешной публикации старый MP3 MUST быть перемещён в `<корень старого файла>\_old\<относительный путь>`, а его `.lrc` — вместе с ним. При MP3-fallback или ошибке публикации старый файл MUST NOT перемещаться. При занятом имени в `_old` MUST добавляться метка времени.

#### Scenario: MP3 заменён на FLAC

- **WHEN** пользователь подтвердил обновление MP3 из `LIBRARY_DIR`, сервер отдал `flac` или `flac-mp4`, а ffmpeg доступен
- **THEN** новый `.flac` с тегами появляется в `OUTPUT_DIR`, старый MP3 перемещается в `LIBRARY_DIR\_old`, новых аудиофайлов в `LIBRARY_DIR` нет

#### Scenario: MP3 из загрузок обновлён

- **WHEN** пользователь подтвердил обновление MP3 из `OUTPUT_DIR`
- **THEN** новый `.flac` появляется в `OUTPUT_DIR`, старый MP3 перемещается в `OUTPUT_DIR\_old`

#### Scenario: Сайдкар старого файла

- **WHEN** рядом со старым MP3 есть `.lrc`
- **THEN** файл `.lrc` перемещается в `_old` вместе со старым MP3

#### Scenario: Lossless снова пропал

- **WHEN** во время обновления сервер вернул MP3-fallback
- **THEN** новый MP3 не публикуется как обновление, старый файл остаётся на месте, в логе указана причина

#### Scenario: Ошибка публикации

- **WHEN** скачивание или тегирование завершилось ошибкой
- **THEN** временный файл удаляется, старый файл остаётся на месте, в логе есть ошибка

#### Scenario: Имя в _old занято

- **WHEN** в `_old` уже есть файл с тем же относительным путём
- **THEN** старый файл сохраняется под именем с меткой времени, новый FLAC остаётся в `OUTPUT_DIR`

### Requirement: Существующий FLAC и повторный запуск

Если FLAC с тем же треком уже есть рядом со старым MP3 или в `OUTPUT_DIR`, приложение MUST NOT скачивать второй; оно MUST проверить, что это тот же трек, и предложить только переместить дубль MP3 в `_old`. После успешного обновления файл MUST исчезнуть из кандидатов. Прерванная job'а MUST сохранять уже обновлённые файлы и при следующем запуске продолжать с необновлённых.

#### Scenario: FLAC уже лежит рядом

- **WHEN** рядом с MP3 уже есть `.flac` с тем же треком
- **THEN** повторного скачивания нет, предлагается только переместить MP3 в `_old`

#### Scenario: FLAC уже есть в загрузках

- **WHEN** в `OUTPUT_DIR` уже есть `.flac` с тем же треком, а старый MP3 лежит в `LIBRARY_DIR`
- **THEN** повторного скачивания нет, старый MP3 перемещается в `LIBRARY_DIR\_old`

#### Scenario: Остановка посреди пачки

- **WHEN** пользователь остановил обновление после нескольких треков
- **THEN** уже обновлённые файлы остаются, незавершённые не считаются обновлёнными, следующая проверка продолжает с них

#### Scenario: Повторная проверка после обновления

- **WHEN** трек уже обновлён до `.flac`
- **THEN** он больше не появляется в списке найденного

### Requirement: Логи

Проверка, обновление, отклонение и возврат MUST писать в лог понятные строки на русском: начало и итог проверки, найденные треки, обновление, причину отказа или ошибки, отклонённый и возвращённый кандидат. При отсутствии находок MUST быть только итоговая строка. Токен и `Authorization` MUST NOT попадать в лог.

#### Scenario: Найдены треки

- **WHEN** проверка нашла lossless-варианты
- **THEN** в логе есть итог проверки и строки о найденных/обновлённых треках

#### Scenario: Ничего не найдено

- **WHEN** проверка не нашла ни одного варианта
- **THEN** в логе есть только итоговая строка проверки

#### Scenario: Ошибка проверки

- **WHEN** проверка остановлена из-за токена, прав или сети
- **THEN** в логе есть понятная причина на русском, а токен не раскрыт

#### Scenario: Отклонение в логе

- **WHEN** пользователь отклонил поисковое совпадение
- **THEN** в логе есть локальный файл и найденный трек, а токен не раскрыт

#### Scenario: Возврат в логе

- **WHEN** пользователь вернул отклонённое совпадение
- **THEN** в логе есть локальный файл и найденный трек, а токен не раскрыт

### Requirement: Явное отклонение поискового совпадения

Пользователь MUST иметь возможность отклонить поисковое совпадение в окне найденного, не скачивая его. Отклонение MUST сохраняться для локального файла и идентификатора найденного трека. Несколько отклонений одного файла MUST храниться независимо и MUST NOT затирать друг друга. Отклонённый кандидат MUST NOT предлагаться для этого файла до явной отмены. Отклонение MUST NOT менять, перемещать или удалять аудиофайл.

#### Scenario: Кандидат отклонён

- **WHEN** пользователь нажал «Не тот трек» у поискового совпадения
- **THEN** кандидат исчезает из списка, аудиофайл остаётся на месте, а отклонение сохраняется

#### Scenario: Второй кандидат отклонён

- **WHEN** пользователь отклонил второго кандидата для того же локального файла
- **THEN** оба отклонения сохранены, и ни один из отклонённых кандидатов не предлагается

### Requirement: Проверка после отклонения

После отклонения локальный MP3 MUST оставаться кандидатом мониторинга. Приложение MUST сбросить результат проверки, из-за которого файл считался lossless, и при следующей проверке MUST искать другие совпадения, исключая отклонённые. Если все найденные кандидаты отклонены, следующая проверка файла MUST быть назначена не позднее чем через 7 дней.

#### Scenario: Другая версия

- **WHEN** после отклонения запускается следующая проверка
- **THEN** файл снова проверяется, отклонённый кандидат исключается, а другое совпадение может быть предложено

#### Scenario: Все кандидаты отклонены

- **WHEN** для файла отклонены все найденные кандидаты
- **THEN** следующая проверка файла назначается не позднее чем через 7 дней

### Requirement: Возврат отклонённого совпадения

Пользователь MUST иметь возможность отменить отклонение. Возврат MUST удалять запись об отклонении и снова делать кандидата доступным для предложения без автоматического скачивания. Если сохранённые метаданные позволяют, кандидат MUST снова появляться в списке найденного сразу; иначе — при следующей проверке. Возврат MUST обновлять бейдж и список найденного.

#### Scenario: Возврат из настроек

- **WHEN** пользователь нажал «Вернуть» у отклонённого совпадения
- **THEN** запись об отклонении удаляется, кандидат снова доступен для предложения, а скачивание не запускается

#### Scenario: Кандидат сразу в списке

- **WHEN** для отклонённого совпадения сохранены метаданные найденного трека
- **THEN** после возврата кандидат сразу появляется в списке найденного и в бейдже

#### Scenario: Повторный отказ

- **WHEN** пользователь снова отклонил возвращённое совпадение
- **THEN** оно опять скрывается и не предлагается до следующего возврата
