# Design

## Context

См. `proposal.md` — Why. Текущий UI — один `src/frontend/dist/index.html` (~1113 строк) с inline CSS и JS, без сборки; `src/frontend/embed.go` встраивает `dist/*` в exe. Wails v2 открывает окно 950×634, но не задаёт `MinWidth`/`MinHeight`, `BackgroundColour` и `Windows.Theme`; exe собирается `go build`, поэтому не получает иконку, версию и манифест. Тест `tests/statusbar_check.js` извлекает inline-скрипт из `index.html` и гоняет сценарии статусбара в VM с DOM-стубом.

Активный change `add-flac-quality-monitor` меняет тот же `index.html` и дельты `desktop-app`/`app-settings`; реализацию этого редизайна нужно начинать после его архивации.

Ограничения: один exe, WebView2, русские тексты, отсутствие новых runtime-зависимостей, сохранение текущих биндингов и событий, никаких изменений в downloader/resolver/tagger/library/quality.

## Goals / Non-Goals

**Goals:**

- Ввести цельную визуальную систему Warm Vinyl и единые состояния контролов.
- Сделать главный экран понятным в состояниях ожидания, предпросмотра, загрузки, завершения и ошибки.
- Убрать консольную подачу из основного сценария, сохранив технический лог.
- Перестроить настройки так, чтобы они помещались в окно и не теряли изменения.
- Закрыть базовые требования доступности и брендинга окна/exe.
- Сохранить vanilla HTML/CSS/JS и один exe.

**Non-Goals:**

- Светлая тема, кастомные шрифтовые файлы, обложки в списке треков.
- Новые функции скачивания, плеер, библиотека, очередь с паузой.
- Frameless-окно с собственными кнопками управления.
- Изменение API, ключей `.env` и бизнес-логики загрузки.
- Замена Wails на другой UI-стек.

## Decisions

### D1. Разделить фронтенд на `index.html`, `app.css`, `app.js`

Решение: оставить vanilla-стек, но вынести стили и скрипт из монолита. `//go:embed dist/*` уже включает файлы из корня `dist`, поэтому `app.css` и `app.js` не требуют изменения embed. `tests/statusbar_check.js` переключается с извлечения `<script>` на чтение `app.js`; сценарии и DOM-стуб сохраняются.

Альтернативы:

- Оставить один файл — меньше изменений, но 1113 строк inline-кода мешают поддерживать дизайн-систему и тестировать состояния.
- React/Tailwind — отвергнуто: новый шаг сборки, вес и усложнение одного exe.

Риск: `dist/*` не включает подкаталоги. Если позже понадобятся шрифты/картинки, embed нужно расширить; в этом change дополнительных подкаталогов нет.

### D2. Визуальная система Warm Vinyl

Решение: CSS-переменные в `:root` и компонентные классы. Ключевая палитра:

```text
--bg:          #12100F
--surface:     #1C1817
--surface-2:   #26201E
--border:      #3A302D
--text:        #F5EEE8
--text-muted:  #B7A8A0
--accent:      #F0A35E
--accent-hover:#FFB877
--accent-ink:  #1A120D
--success:     #8FD3A0
--warning:     #E8C468
--danger:      #E06C5F
--focus:       #FFC98A
```

Типографика: `Segoe UI Variable Text, Segoe UI, system-ui` для интерфейса; `Segoe UI Variable Display` для заголовков; `Cascadia Mono, Consolas` только для лога и технических значений. Базовый размер 14 px, вторичный 13 px, подпись 12 px, заголовки 20–24 px; `font-variant-numeric: tabular-nums` для процентов и байтов.

Сетка: отступы 4/8/12/16/24/32, радиусы 8/10/14, границы 1 px, focus-ring 2 px с offset 2 px. Анимации 140–180 мс, `prefers-reduced-motion` отключает переходы.

Альтернативы: палитра Yandex Yellow и нейтральная Graphite Mint рассмотрены в аудите; Warm Vinyl выбрана как совпадающая с существующей иконкой и не выглядящая как официальное приложение Яндекса.

### D3. Один state machine главного экрана

Решение: презентационное состояние `idle | preview | active | done | error` в `app.js`; один `render()` переключает блоки. Бэкенд остаётся источником истины для job'ы; UI только отображает события.

```text
idle --ссылка/превью--> preview --download--> active
  ^                                           |
  |                                           +--job-end ok--> done
  |                                           +--job-end stop-> done (stopped)
  |                                           +--job-end err--> error
  +------------------- «Скачать ещё» ---------+
```

Правила:

- `job-start` переводит в `active`, очищает прошлый список и прячет итоговую карточку.
- `tracks` создаёт строки, `track-status` обновляет их на месте, `progress` двигает полосы.
- `job-end` переводит в `done` или `error`; `stopped` — отдельный итог.
- `quality-found` показывает контекстный баннер, а не меняет основной state.
- `job-start` с заголовком «Обновление FLAC» показывает отдельный баннер фоновой задачи и подпись «Остановить обновление», чтобы не выглядело как обычное скачивание.

Удаляем `#prog` как отдельный fallback: бэкенд уже присылает `tracks` даже для одиночного трека (`downloadSingle` вызывает `trackRows`), поэтому достаточно одного списка. Это убирает третье представление прогресса.

Альтернатива: точечно патчить текущий DOM — быстрее, но оставляет конфликтующие индикаторы и дублирование логики.

### D4. Строка трека и форматы

Решение: строка содержит индекс, название, формат-пилюлю, тонкую полосу, размер и человекочитаемый статус. Данные берём из существующих событий: `tracks` (`[id, label]`), `track-status` (`status`, `kind`), `progress` (`pct`, `done`, `total`).

Формат извлекается из стабильного текста статуса (`(FLAC)`, `(MP3)`, `[ALAC->FLAC]`) функцией `parseTrackStatus()` с таблицей тестов. Технические токены остаются в логе. Это компромисс: не меняем Go-контракт событий, но получаем зависимость от словаря статусов; она локализована в одной функции и покрыта тестами.

Альтернатива: добавить в `track-status` структурированное поле `format` — надёжнее, но требует правок Go-тестов и выходит за рамки визуального change. Если словарь начнёт меняться часто, это станет отдельным улучшением.

### D5. Лог, ошибки и повтор

Решение: лог переезжает в `<details id="details">` с summary «Подробности»; по умолчанию закрыт, max-height 220 px, auto-scroll только когда открыт. Ошибка показывается inline над полем ввода, с кнопкой «Повторить». Последняя ссылка хранится только в памяти текущей сессии (`lastLink`), не в localStorage и не в истории; это не нарушает требование об отсутствии истории.

При ошибке панель «Подробности» получает бейдж с количеством ошибок, чтобы технические детали не терялись. Кнопка «Повторить» заполняет поле и вызывает тот же `startDownload()`.

Альтернатива: оставить лог основным каналом — противоречит цели «не консоль».

### D6. Настройки: две колонки, секции и защита изменений

Решение: модалка 720×560 (max 92vw/90vh) с двумя колонками и секциями: Аккаунт, Папки, Качество, Теги, Производительность, Мониторинг. Шапка и footer фиксированы, прокручивается только тело. При минимальном окне 860×600 карточка помещается, «Сохранить»/«Отмена» всегда видны.

Снимок значений формы делается при открытии; `isDirty()` сравнивает текущие значения со снимком. Закрытие по Escape, фону или крестику при изменениях открывает встроенный confirm-диалог, а не `window.confirm`; «Отмена» — явный отказ без вопроса. Это сохраняет стиль и не зависит от системного MessageBox.

Фокус: при открытии — первое поле; Tab циклически внутри карточки; при открытой справке токена её trap имеет приоритет, после закрытия фокус возвращается на ссылку «Как получить токен?», затем в настройки. После закрытия настроек — в поле ссылки (см. `desktop-app`).

Альтернатива: отдельная страница настроек — больше навигации для 13 параметров; side sheet — красиво, но отнимает место у главного экрана. Две колонки — компромисс.

### D7. Доступность

Решение:

- `role="dialog"`, `aria-modal="true"`, `aria-labelledby` для всех модалок; `aria-hidden` синхронизируется с классом `.open`.
- `aria-live="polite"` для агрегированного прогресса и терминальных статусов; `role="alert"`/`aria-live="assertive"` для ошибок. Не объявлять каждый байт: только смену трека, 25/50/75/100% и финал.
- `role="progressbar"` с `aria-valuemin/max/now` и `aria-label` на общей полосе.
- `aria-label` на icon-only кнопках; видимые tooltip остаются.
- `:focus-visible` для всех интерактивных элементов.
- `prefers-reduced-motion` отключает transitions/animations.
- Проверка контраста: accent-текст на accent-заливке использует `--accent-ink`, а не белый.

Альтернатива: нативные `<progress>`/`<dialog>` — меньше кода, но стилизация в WebView2 и вложенные модалки менее предсказуемы; используем div-модалки с явными ARIA-атрибутами.

### D8. Wails: минимальный размер, фон и тёмный заголовок

Решение в `src/cmd/app/main.go`:

```go
Width:  width,
Height: height,
MinWidth:  ui.MinWindowWidth,   // 860
MinHeight: ui.MinWindowHeight,  // 600
BackgroundColour: &options.RGBA{R: 18, G: 16, B: 15, A: 255},
Windows: &windows.Options{Theme: windows.Dark},
```

Константы `MinWindowWidth`/`MinWindowHeight` живут в `internal/ui` и покрываются тестом. `BackgroundColour` убирает белую вспышку (Wails по умолчанию ставит белый фон), `Windows.Theme` делает системный заголовок тёмным. Native title bar сохраняем — frameless требует своей обработки перетаскивания, кнопок и доступности.

Альтернатива: `Frameless: true` + кастомный title bar — стильнее, но повышает риск и объём; вынесено за скоуп.

### D9. Иконка, версия и манифест exe

Решение: добавить `assets/icon.ico` (multi-size, производный от `assets/icon.png`) и конфиг ресурсов Windows. В `scripts/build-windows.ps1` перед `go build` генерировать временный `.syso` через закреплённую версию `go-winres` (`go run ...`), затем собирать exe и удалять `.syso`. В ресурсы входят:

- `RT_GROUP_ICON` из `assets/icon.ico`;
- `RT_VERSION`: `ProductName`, `FileDescription`, `FileVersion`/`ProductVersion` из файла `version`;
- `RT_MANIFEST` с `dpiAware`/`dpiAwareness` PerMonitorV2 и `asInvoker`.

Если генератор недоступен, release-сборка падает с понятной ошибкой; обычная разработка может использовать `go build` без ресурсов, но релизный exe обязан иметь иконку/версию/манифест.

Альтернативы:

- Перейти на `wails build` — канонично, но требует `wails.json`, CLI и меняет текущий проверенный build-скрипт.
- Закоммитить готовый `.syso` — бинарный артефакт в git, плохо ревьюится и устаревает при смене версии.

### D10. Тесты и проверки

Решение:

- `tests/statusbar_check.js` читает `app.js`, сохраняет текущие сценарии и добавляет: статусбар скрыт до первой job'ы; человекочитаемый статус и формат; inline-ошибка и `lastLink`; «Подробности» свёрнуты; защита настроек от потери изменений (насколько позволяет DOM-стуб).
- Go: `window_test.go` — константы минимального размера; `go test ./...`, `go vet ./...`, `go build ./...`.
- Ручной визуальный прогон: 950×634 и 860×600, 125% и 150% масштаб Windows, светлая тема Windows, клавиатурный сценарий Tab/Escape, скриншоты состояний idle/active/done/error и настроек.
- `openspec validate --all`, `python scripts/check-version.py`.

Альтернатива: визуальные regression-тесты через Playwright — новая тяжёлая зависимость; для одного окна достаточно DOM-стенда и ручных скриншотов.

## Risks / Trade-offs

- **Разделение `index.html` ломает текущий тест, который извлекает inline `<script>`** → обновить `tests/statusbar_check.js` в той же задаче; сохранить один IIFE/скрипт в `app.js`.
- **Парсинг формата из текста статуса хрупкий** → централизовать в `parseTrackStatus()`, покрыть таблицей тестов; при изменении словаря менять одну функцию.
- **`//go:embed dist/*` не включает подкаталоги** → держать `app.css`/`app.js` в корне `dist`; при добавлении ресурсов расширить embed отдельной задачей.
- **Две колонки настроек могут быть тесными на 860×600** → карточка 720×560, прокручивается только тело, footer фиксирован; проверить на 125–150% масштабе.
- **Тёмный заголовок Windows может не примениться на старых сборках Windows 10** → остаётся тёмный контент и фон; native frame не ломается, кнопки управления доступны.
- **Генератор ресурсов adds build-зависимость** → закрепить версию, кэшировать, падать с понятным сообщением; не менять runtime-зависимости приложения.
- **Скрытый статусбар до первой загрузки конфликтует со старым сценарием спеки** → сценарий изменён в дельте `track-download`; тест обновляется вместе с UI.
- **Сворачиваемый лог может спрятать причину ошибки** → inline-ошибка и бейдж ошибок на «Подробностях»; лог не единственный канал.
- **Параллельная работа с `add-flac-quality-monitor`** → начинать после архивации; иначе конфликты в `index.html` и дельтах `desktop-app`/`app-settings`.

## Migration Plan

Миграции данных нет: меняются только frontend, Wails-опции и build-ресурсы; `.env`, API и форматы файлов не затрагиваются.

1. Дождаться архивации `add-flac-quality-monitor`.
2. Фаза 0: токены, `app.css`, тёмные контролы, SVG-иконки, empty state, min size, `BackgroundColour`, `Windows.Theme`.
3. Фаза 1: state machine, превью-карточка, список треков, итоговая карточка, inline-ошибки, «Подробности».
4. Фаза 2: две колонки настроек, секции, sticky footer, dirty guard, focus trap.
5. Фаза 3: ARIA/`aria-live`, reduced motion, иконка/версия/манифест exe.
6. Проверки и релиз по обычному процессу `release.ps1`; версия меняется только в релизе.

Откат: `git revert` изменения фронтенда и build-скрипта; пользовательские данные и `.env` не мигрируются, поэтому откат безопасен. Старый UI остаётся в истории git.

## Open Questions

Нет вопросов, меняющих спецификации или подход. Точная версия и синтаксис `go-winres`, а также необходимость конвертации PNG→ICO уточняются в первой задаче фазы 3; при недоступности инструмента альтернатива — `wails build` — рассматривается только если генератор ресурсов окажется неработоспособным.
